# CLAUDE.md

Guidance for Claude Code working in this repository. Read this before making changes, and keep it updated as the infrastructure and our working agreements evolve.

## What this repo is

Infrastructure-as-Code for zanyhunter's homelab. The goal is disaster recovery: everything needed to stand up equivalent infrastructure on fresh hardware should be reconstructable from this repo plus the age private key (kept in KeePass, see Secrets below). Nothing here currently hosts real user data — the Kubernetes cluster is dev-only — but the Cloudflare DNS token controls a real, internet-facing domain, so treat that boundary seriously even though the cluster itself is disposable.

The Tofu config is also meant to be **reusable across multiple cluster environments (dev today, a future prod) for years to come** — and dev/prod will not share infrastructure (each gets its own NFS backend, for instance). Environment-specific values (Helm chart versions, the NFS storage server/share, etc.) belong in object-typed variables in each unit's `variables.tf` (see `cluster`, `chart_versions`, `nfs_storage`) with real values in that environment's `tofu/live/<env>/env.hcl` (see `docs/src/bootstrap-environment/10-terragrunt-units.md`), not hardcoded in resource blocks — when adding a new add-on or resource with a version string or environment-specific setting, variablize it the same way rather than hardcoding it "for now."

## Physical & network topology

- **Compute**: 3 physical Proxmox nodes (`pve-node-0/1/2`) in a hyperconverged cluster (`homelab`) using Ceph for storage (`ceph-1` datastore).
- **Storage**: 1 NFS NAS for service data (Immich, etc.). Not yet under IaC management — provisioned/configured manually today. Revisit if it should be brought into Tofu or get its own IaC story.
- **Network**: Unifi-managed. The K8s cluster lives on VLAN 1601, subnet `192.168.160.0/27` (expanded from a `/28` once that filled up — see issue #3), gateway `192.168.160.1`, domain `k8s.thepugh.family` (see the `network` unit, `tofu/modules/network/main.tf`). Local DNS resolution for that domain is a wildcard record in the Unifi controller pointing at the MetalLB ingress IP — documented in `docs/src/bootstrap-environment/04-dns-configuration.md`.
- **Real external domain**: `thepugh.family`, managed in Cloudflare. cert-manager uses a Cloudflare API token (DNS Zone Edit scope) for ACME DNS-01 challenges — this is the one credential in this repo with blast radius outside the homelab.

## Kubernetes cluster

- Talos Linux, provisioned as Proxmox VMs via the `siderolabs/talos` and `bpg/proxmox` Tofu providers.
- 6 nodes today: `k8s-ctrl-00/01/02` (control plane) + `k8s-node-00/01/02` (worker), one of each role per Proxmox node — see `tofu/live/dev/env.hcl`.
- Cluster name `dev`, endpoint `192.168.160.16` — a Talos-managed floating VIP shared across the 3 control planes (not any single node's address), so the control plane stays reachable if one control-plane node is down.
- **Terragrunt units**: the Tofu config is seven independently-applied units (`tofu/modules/{network,talos-cluster,core-addons,backup,keycloak-infra,keycloak-realm,observability}/`, wired by `tofu/live/{dev,prod}/*/terragrunt.hcl`), not one flat root module. A from-scratch stand-up or full teardown is one command — `terragrunt run --all --non-interactive -- apply -auto-approve` (or `destroy`) from `tofu/live/dev/` — verified live via a real destroy-then-recreate of the entire dev environment. Detailed docs: `docs/src/bootstrap-environment/10-terragrunt-units.md`.
- Bootstrap add-ons (the `core-addons` unit): MetalLB, ingress-nginx, cert-manager, csi-driver-nfs/StorageClass, ArgoCD (HA, exposed at `argocd.k8s.thepugh.family`). Cluster-level *config* objects that used to be applied by Tofu `terraform_data`/`local-exec` provisioners — the MetalLB `IPAddressPool`/`L2Advertisement` (LB pool `192.168.160.5-8`, `192.168.160.12-14`) and the `letsencrypt-prod`/`letsencrypt-staging` cert-manager `ClusterIssuer`s — are GitOps-managed now instead; see the app-of-apps entry below.
- **App-of-apps**: an ArgoCD `ApplicationSet` (part of the `core-addons` unit, `var.gitops` for repo/revision) auto-discovers one `Application` per directory under this repo's `apps/`, so adding a new app is "add a directory under `apps/`, push" — no Tofu change, no manual `kubectl`/`argocd` command. `apps/cluster-addons/` is the cluster-level-config directory mentioned above; real workloads (Immich, etc.) will each get their own `apps/<app>/` directory when they land. Detailed docs: `docs/src/bootstrap-environment/06-gitops.md`.
- **Backup**: Velero + MinIO (the `backup` unit), also Tofu/Helm-managed rather than GitOps — MinIO is an S3-compatible gateway in front of the NFS share (its own data volume is just another PVC on the `nfs_storage`-backed StorageClass), and Velero backs up Kubernetes object definitions to it on a daily schedule (`var.backup`). File-system/volume-snapshot backup is deliberately disabled since everything today is already NFS-backed and separately protected by the NAS's own offsite backup. Detailed docs, including the restore procedure: `docs/src/bootstrap-environment/07-backup-restore.md`.
- **SSO**: Keycloak + a hand-rolled Postgres `StatefulSet` (the `keycloak-infra` unit), reachable at `keycloak.k8s.thepugh.family`. The `homelab` realm and its OIDC clients (the `keycloak-realm` unit) are managed declaratively via the `keycloak` Terraform provider — same pattern as `unifi_network.this` — authenticating with the same Tofu-generated bootstrap admin credentials Keycloak itself is given. Splitting Keycloak's bootstrap from its realm config into two Terragrunt units (rather than one `tofu/sso.tf`) is what eliminated the old `-target=time_sleep.wait_for_keycloak` two-phase bootstrap for good — see `docs/src/bootstrap-environment/10-terragrunt-units.md`. An oauth2-proxy + `whoami` forward-auth demo at `sso-demo.k8s.thepugh.family` is a permanent reference deployment, not a throwaway — it's the copy-paste template for real apps that need forward-auth.
- **Observability**: kube-prometheus-stack (Prometheus + Alertmanager + Grafana + node-exporter + kube-state-metrics) plus Loki + Grafana Alloy for logs (the `observability` unit), all Tofu/Helm-managed, sibling to `backup`/`keycloak-infra` in the dependency graph. Grafana is reachable at `grafana.k8s.thepugh.family`; default cluster/node dashboards and most baseline alerts (node down, PVC nearly full, etc.) come from the chart's own defaults for free. Alertmanager routes to a Discord webhook (`discord_alert_webhook` in `tofu/secrets.enc.yaml`). cert-manager certificate-expiry and Velero backup-staleness alerts are added via the chart's own `additionalPrometheusRulesMap`/`additionalScrapeConfigs` values rather than separate `ServiceMonitor`/`PrometheusRule` custom resources in `core-addons`/`backup` — those would need this unit's Prometheus Operator CRDs to exist before `core-addons`/`backup` apply, which is backwards in the DAG. Detailed docs: `docs/src/bootstrap-environment/11-observability.md`.
- **NetworkPolicies + Pod Security Admission**: every namespace this repo manages is default-deny on ingress and egress, with explicit allow rules for the traffic it actually needs, plus an explicit PSA level (`restricted` where a chart supports it, `baseline` where a one-shot Helm hook Job doesn't expose enough of a `securityContext` to reach `restricted`, `privileged` only for the 3 namespaces with a genuine `hostNetwork`/`hostPID`/`hostPath` need — `metallb-system`, `csi-driver-nfs`, `monitoring`). Lives as `kubernetes_network_policy`/namespace-label resources directly in whichever unit already owns that namespace, referencing other namespaces by their automatic `kubernetes.io/metadata.name` label rather than any new Terragrunt `dependency` wiring. Detailed docs, including the specific chart-default gaps found live: `docs/src/bootstrap-environment/12-network-policies.md`.
- **Remote Tofu state**: a plain `local` backend per unit, all rooted under `tofu/state/` — a gitignored directory meant to be an SMB mount of a NAS share, set up out-of-band (not Tofu-managed) — chosen specifically so state storage never depends on infrastructure this config itself creates/destroys (no "destroying your own state backend" risk on a full teardown) and without introducing a new external dependency (cloud object storage). Each unit's exact path is generated by `tofu/live/root.hcl`'s `remote_state` block from directory structure, not hand-typed. See `docs/src/bootstrap-environment/09-remote-state.md` for the SMB mount setup.
- **Dev/prod separation**: `tofu/live/dev/` is the only live environment; `tofu/live/prod/` has the identical six-unit shape with placeholder `env.hcl` values but has never been applied. Standing up a real prod needs: a real unallocated VLAN/subnet (Unifi sign-off — one VLAN per cluster, tied to that cluster's own lifecycle, per the standing guardrail below), non-colliding vm_id/IP ranges, a dedicated NFS export, and a real per-environment ingress-hostname scheme (today every hostname is still a hardcoded literal, e.g. `argocd.k8s.thepugh.family` — two environments live at once would collide on these; unstarted follow-up work). See `docs/src/bootstrap-environment/10-terragrunt-units.md`.

## Toolchain

- **OpenTofu** (not Terraform) — `tofu` CLI. **Terragrunt** orchestrates it (see Kubernetes cluster section above) — config lives in `tofu/modules/` (plain Tofu root modules, one per unit) and `tofu/live/` (per-environment Terragrunt wiring); commands are run as `terragrunt ...` from a `tofu/live/<env>/<unit>/` directory (or `tofu/live/<env>/` for `run --all`), not `tofu ...` directly. Detailed docs: `docs/src/bootstrap-environment/10-terragrunt-units.md`. State lives on an SMB-mounted NAS share — a fresh machine needs that share mounted at `tofu/state/` before running `terragrunt init`, or Tofu will happily create fresh empty local state files instead of finding the real ones.
- **sops** + **age** — secrets encryption, see below. Both installed locally.
- **gh CLI** — installed and authenticated as ZanyHunter over HTTPS. Used for the branch/PR workflow (see Git workflow below).
- **mdBook** — installed (`~/.cargo/bin/mdbook`). Docs source is `docs/src/`; the built site `docs/book/` is gitignored (not committed) — run `mdbook build docs` locally to preview, no need to commit output.
- **kubectl** — this session's Bash environment has confirmed LAN reachability to `192.168.160.0/27` (verified via `ping` to a control-plane node and the gateway, 2026-08-27) — don't assume otherwise. If `ping`/`kubectl` fail, check first rather than declaring an environment limitation: the cluster's CA/certs regenerate on every from-scratch rebuild, so a cached `~/.kube/config` from before a rebuild will fail TLS verification even though the network path is fine — fetch a current one with `terragrunt output -raw kube_config` (from `tofu/live/dev/talos-cluster/`) rather than assuming a stale kubeconfig is still valid.
- **velero CLI** — not installed as part of cluster bootstrap; download the release matching the server's `appVersion` (`chart_versions.velero` in `tofu/live/dev/env.hcl` pins the Helm chart, whose `Chart.yaml` `appVersion` is the matching CLI/server version) from the [velero releases page](https://github.com/vmware-tanzu/velero/releases) when needed. See `docs/src/bootstrap-environment/07-backup-restore.md`.

## Secrets management

Provider credentials (Proxmox, Unifi, Cloudflare) live encrypted at `tofu/secrets.enc.yaml`, committed to git. Encrypted with SOPS, recipient is a single age keypair.

- **Decryption**: Terraform reads the file automatically via the `carlpett/sops` provider at plan/apply time — no manual decrypt step needed for normal Tofu usage. Since the Terragrunt refactor, the actual `data "sops_file"` block is generated per-unit from `tofu/live/root.hcl`'s `secrets_tf` local, only into the units that need decrypted credentials (`network`, `talos-cluster`, `core-addons`, `observability`) — see `docs/src/bootstrap-environment/10-terragrunt-units.md`.
- **Manual edit**: `sops tofu/secrets.enc.yaml` (opens decrypted in `$EDITOR`, re-encrypts on save).
- **The age private key** lives at `~/.config/sops/age/keys.txt` on this machine (mode 600) — that's the default lookup path for both `sops` and the Terraform provider. It is **not** in git and never should be.
- **Disaster recovery for the key itself**: the private key is backed up in the user's KeePass file, which is itself stored offsite separately from this repo. If this machine is lost, recover the key from KeePass and place it back at `~/.config/sops/age/keys.txt` before running `tofu` commands.
- **Design note**: this is a single age key covering all secrets (Proxmox, Unifi, Cloudflare) — an honor-system boundary, not a technical one. We considered splitting Unifi/Cloudflare into a separately-keyed file so Claude could be structurally prevented from touching them, and decided against it: the user has a fresh full Unifi backup, so the blast radius of an honor-system violation is a few minutes of restore time. Revisit this if that risk tolerance changes.
- **GitOps secrets (ksops)**: ArgoCD's repo-server also has this same age key, mounted as a `kubernetes_secret` in the `argocd` namespace (the `core-addons` unit, `tofu/modules/core-addons/main.tf`), so it can decrypt SOPS-encrypted manifests under `apps/` at sync time via [ksops](https://github.com/viaduct-ai/kustomize-sops). This means the raw private key now lives in one additional place beyond this machine + KeePass: as a live Kubernetes Secret in-cluster. Accepted for the same reason as the single-key design above (dev cluster, single operator); revisit alongside that note if the risk tolerance changes. See `docs/src/bootstrap-environment/06-gitops.md` for how to add a new encrypted secret this way.

## Standing permissions & guardrails

- **Proxmox and Kubernetes (dev cluster)**: full autonomy. Run `terragrunt`/`tofu plan`/`apply`/`destroy`, `kubectl`, `helm` freely against this stack without asking first — it's dev-only and disposable.
- **Unifi**: do **not** author or apply changes to Unifi-managed Tofu resources (currently `unifi_network.this`, in the `network` unit, and the `unifi` provider block) that change what's actually deployed — new Unifi resources, address space changes, or any other config change — without asking the user first. It does **not** mean avoiding the files entirely: read-only operations (`tofu plan`) and mechanical formatting (`tofu fmt` and similar tools) are fine even if they happen to touch a line inside a Unifi resource block, since those don't change intent or behavior. **Exception, explicitly authorized**: each cluster (dev today, a future prod) has exactly one Unifi VLAN tied to that cluster's own lifecycle — standing it up or tearing it down as part of a normal cluster destroy/recreate cycle is pre-approved and needs no per-instance sign-off or `-target` workaround, as long as its configuration doesn't change in the process.
- **Cloudflare/DNS**: same ask-first treatment as Unifi. The token controls a real domain; cert-manager's existing use of it (DNS-01 challenges) is already approved and needs no further confirmation, but any new Cloudflare-related Tofu resource or config change should be proposed and confirmed before applying.
- **Everything else** (docs, non-secret Tofu resources, CI config, etc.): normal judgment — no special standing restriction beyond the git workflow below.

## Git workflow

- **Commit messages**: Conventional Commits, always (`feat:`, `fix:`, `docs:`, `chore:`, etc., with a scope where it adds clarity, e.g. `feat(tofu): ...`). Split unrelated concerns into separate, self-consistent commits rather than one large commit — each commit should leave the repo in a valid state.
- **Branching**: do not push directly to `main`. Create a feature branch, commit there, push it, and open a PR with `gh pr create`. Wait for the user to review and merge — do not merge PRs unilaterally.
- **Branch naming**: `type/short-description` (e.g. `feat/argocd-app-of-apps`, `docs/dns-guide`), mirroring the commit type.

## Tasking workflow

How the user hands off work, especially for larger refactors/features tracked over multiple sessions:

- **GitHub Issues are the backlog.** One issue per larger refactor or feature, with a checklist of subtasks in the body. Claude Code does not retain memory across sessions by default, so an issue is durable state a future session can re-read cold — treat it as more reliable than chat history for "what are we doing and why."
- **No passive awareness.** Claude does not see new GitHub comments, issues, or PR activity as they happen — only when a session actively runs a `gh` command. Nothing happens automatically just because something was posted on GitHub.
- **To task Claude**: point it at the issue number in a live session (e.g. "pick up #4"). It should pull the issue via `gh issue view`, do the work with full local access (secrets, LAN, everything this environment has), open a PR per the Git workflow above, and comment back on the issue linking the PR (or close it once merged).
- **The `@claude` GitHub App/Action integration** (triggers an automated run when `@claude` is mentioned in an issue/PR, no local session needed) was considered and deliberately skipped for now: that integration runs on an isolated GitHub Actions runner with access only to the git repo and configured Actions secrets — no local machine access, meaning no age key and no LAN reachability. Since nearly everything in this repo eventually touches secrets or needs LAN access, it would only cover a narrow slice of work (pure code review/refactor suggestions). Revisit if the balance of work shifts toward tasks that don't need local access.
- **GitHub Projects** (kanban board over issues) is worth adding once more than 3-4 larger initiatives are in flight concurrently; not needed yet.

Keep `docs/src/` in sync with infrastructure changes as part of the same change/PR — when a Tofu change alters bootstrap steps, add-ons, or operational procedure, update the relevant mdBook page(s) alongside it rather than letting docs drift.

## History / key decisions

- Chose SOPS + age over a NAS-hosted secrets store (e.g. Vault/MinIO) specifically because the user wanted secrets to survive a NAS-down disaster; encrypted secrets committed to git satisfy that, since any clone of the repo has the ciphertext, and only the age key (KeePass-backed, offsite) is the recovery-critical piece.
- Migrated `tofu/secrets.auto.tfvars` (plaintext, gitignored, single point of failure) to `tofu/secrets.enc.yaml` + `carlpett/sops` provider — see commit `1625bc3`.
- Decided against the `@claude` GitHub App/Action integration for now, in favor of GitHub Issues as backlog + live-session tasking — see Tasking workflow above for the reasoning (local secrets/LAN access it can't replicate).
- Bootstrapped the ArgoCD app-of-apps ApplicationSet and wired ksops into the repo-server for GitOps-managed secrets, migrating the MetalLB pool and cert-manager `ClusterIssuer`s off Tofu `terraform_data`/`local-exec` in the process — see PR #22 (closed issues #6, #7). ksops/SOPS-in-ArgoCD was chosen over External Secrets Operator/Vault specifically to avoid running and securing a new component, extending the same age-key pattern already used for `tofu/secrets.enc.yaml`.
- Deployed Velero + MinIO for cluster backups (closed issue #8) — MinIO because Velero needs an S3 API and doesn't speak NFS natively, so it's the gateway in front of the NFS share rather than a separate secrets-style store (see the SOPS-vs-MinIO decision above, which is about a different concern). Verified with a real backup → delete-namespace → restore round-trip, not just a `Completed` status.
- Deployed Keycloak + Postgres for SSO (closed issue #9), with the realm/clients managed via the `keycloak` Terraform provider rather than a Job/script — extends the same "declarative provider talks to the app's own API" pattern already used for `unifi_network.this`. Postgres is a hand-rolled `StatefulSet` rather than a chart, for the same pinned-version reason MinIO avoided Bitnami (see the backup decision above). Verified with a real end-to-end login (not just "the client exists"): scripted the full OIDC authorization-code flow against the `demo` realm user through oauth2-proxy forward-auth, confirming `X-Auth-Request-User`/`-Email` reached the protected app.
- Moved Tofu state off local-only storage (closed issue #12). First attempt was a remote S3 backend on the existing MinIO instance (a new `tofu-state` bucket, exposed via a new Ingress since MinIO had no reachable endpoint outside the cluster) — worked, including a real verified test of OpenTofu's native S3 conditional-write locking (two concurrent `tofu plan` runs, the second rejected with a `412 PreconditionFailed`), but was reverted after recognizing a structural problem: MinIO is created *by* this Tofu config, so destroying the cluster would eventually destroy the very thing backing its own state, and the final state-persist write would fail as a result. Replaced with a plain `local` backend pointed at a gitignored directory meant to be an SMB mount of a NAS share, set up out-of-band — the NAS already backs every cluster's NFS storage and already has its own offsite backup, and unlike the MinIO approach, state storage now depends on nothing this config itself creates or destroys, for any cluster (dev, a future prod, or otherwise). Also surfaced the same structural point either approach shares: backend blocks can't reference variables, so the backend's location is a hardcoded literal — exactly what prompted filing issue #26 (Terragrunt) as future work.
- Adopted Terragrunt, splitting the monolithic root module into six independently-applied units (closed issues #21, #26) — see `docs/src/bootstrap-environment/10-terragrunt-units.md`. Fixes the Keycloak two-phase bootstrap for good (splitting `keycloak-infra`/`keycloak-realm` means `dependency` blocks, not `-target`, enforce ordering) and gives real dev/prod separation (each environment is its own directory of the same six units, `prod` scaffolded with placeholder values but never applied). Existing live state was migrated resource-by-resource via `tofu state mv` into each unit's new state file, verified zero-diff before any old file was deleted. Verified live with a real full destroy-then-recreate of the entire dev environment (not just "the config validates") — caught and fixed three genuine bugs in the process: `helm_release.ingress_nginx` needed `wait = false` (Helm's default wait-for-LoadBalancer-IP behavior deadlocks on a from-scratch bootstrap, since MetalLB's IPAddressPool is GitOps-managed and can't exist until ArgoCD — which depends on ingress-nginx — has already synced); every `dependency` block's `mock_outputs_allowed_terraform_commands` needed `"destroy"` added (without it, `run --all destroy` couldn't clean up a stack a failed apply had left partially applied, since a downstream unit hard-fails resolving a dependency with no real outputs yet — safe to allow, since a unit with nothing to destroy never touches its provider regardless, and `"apply"` stays deliberately excluded so the Keycloak fix above is unaffected); and oauth2-proxy's Ingress needed `nginx.ingress.kubernetes.io/proxy-buffer-size: "16k"` (its session cookie bundling Keycloak's access/ID/refresh tokens routinely exceeded ingress-nginx's default buffer, 502ing every real login — a pre-existing bug on the original flat module too, just never hit before; re-verified with the same real scripted-login bar used for #9). Repeated back-to-back destroy/recreate cycles against the same 3 physical Proxmox nodes (done deliberately, beyond what was asked, to pressure-test the one-command claim under adverse conditions) also surfaced real but environmental flakiness — a transient DNS failure resolving `factory.talos.dev`, and Talos VMs that repeatedly failed to become network-reachable for several cycles in a row even though Proxmox reported them created — both resolved by simply retrying once the physical hardware had a chance to settle, not a defect in the refactor.
- Deployed an observability stack — kube-prometheus-stack (Prometheus/Alertmanager/Grafana/node-exporter/kube-state-metrics) + Loki + Grafana Alloy for logs (closed issue #14), a seventh Terragrunt unit sibling to `backup`/`keycloak-infra`. Alertmanager routes to a Discord webhook; cert-manager cert-expiry and Velero backup-staleness alerts are added via the chart's own `additionalPrometheusRulesMap`/`additionalScrapeConfigs` values rather than separate `ServiceMonitor`/`PrometheusRule` custom resources in `core-addons`/`backup`, specifically to avoid a real CRD-before-CR ordering conflict those units' earlier-in-the-DAG position would create. Verified live, not with a mocked-up "the pods are Running" check: a synthetic alert POSTed directly to Alertmanager was confirmed to actually arrive in Discord by the user watching the channel. Two real Talos incompatibilities were found and fixed in the process: kube-prometheus-stack's default `kube-proxy`/`kube-scheduler`/`kube-controller-manager` scrape jobs assume kubeadm-style host-network exposure that Talos doesn't provide (bound to loopback only), producing permanent `TargetDown` alerts until those three jobs and their default alert-rule groups were disabled; and Loki's `chunksCache` (an optional memcached query-cache, on by default) requests ~8Gi of memory — more than any single node in this 4GB-RAM-per-node cluster has — leaving it permanently unschedulable until disabled, the same class of oversized-chart-default problem already hit once with MinIO. See `docs/src/bootstrap-environment/11-observability.md`.
- Rolled out default-deny NetworkPolicies plus an audited/tightened Pod Security Admission level across every namespace this repo manages (closed issue #31, split from #13 at the user's request into three focused issues — see #32, #33 for the other two). Applied and verified one namespace group at a time rather than all at once, given the real risk of breaking already-verified functionality — every previously-established verification bar in this repo (a real Velero backup, a real Keycloak/oauth2-proxy login, Grafana/Prometheus/Loki/Discord alerting, ArgoCD sync, a real PVC provisioning) was re-run and passed after its namespace group's rollout, not assumed to still work. `metallb-system`/`csi-driver-nfs`/`monitoring` stay at the already-justified `privileged` level (genuine `hostNetwork`/`hostPID`/`hostPath` needs); `argocd`/`cert-manager`/`ingress-nginx`/`keycloak`/`sso-demo` reached `restricted`; `minio`/`velero` landed on `baseline` after a one-shot Helm hook Job in each (not the main workload) turned out not to expose enough of a `securityContext` value to go further. Found and fixed several real gotchas along the way: an `allow-same-namespace` policy is now unconditional for every namespace rather than judged pod-by-pod, after a default-deny rollout without one left MinIO's own post-install bucket-creation Job hanging with no clear error; Postgres's *existing* data directory turned out to be owned by uid 70, not the uid 999 guessed at first, caught via a throwaway debug pod against the same PVC before it corrupted anything; and a StatefulSet's controller left a crash-looping pod running under its *old* spec for several minutes after a fix was applied, needing a manual pod delete to force it to pick up the correction. See `docs/src/bootstrap-environment/12-network-policies.md`.
