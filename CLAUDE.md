# CLAUDE.md

Guidance for Claude Code working in this repository. Read this before making changes, and keep it updated as the infrastructure and our working agreements evolve.

## What this repo is

Infrastructure-as-Code for zanyhunter's homelab. The goal is disaster recovery: everything needed to stand up equivalent infrastructure on fresh hardware should be reconstructable from this repo plus the age private key (kept in KeePass, see Secrets below). **Dev and prod are not the same kind of thing.** Dev is disposable — nothing real lives there, full autonomy applies (see Standing permissions & guardrails below). Prod is real, in active use, and growing: Immich is a real photo-library app holding real photos, publicly reachable at `photos.thepugh.family`, with more apps expected to be onboarded to public ingress over time. The Cloudflare API token manages real public DNS/Tunnel state for a real, internet-facing domain, not just DNS-01 challenges. Treat prod, its data, and anything with blast radius outside the homelab with the care due any production system — not as disposable infrastructure.

The Tofu config is also meant to be **reusable across multiple cluster environments (dev and prod today, more possible later) for years to come** — and dev/prod do not share infrastructure (each gets its own NFS backend, for instance). Environment-specific values (Helm chart versions, the NFS storage server/share, etc.) belong in object-typed variables in each unit's `variables.tf` (see `cluster`, `chart_versions`, `nfs_storage`) with real values in that environment's `tofu/live/<env>/env.hcl` (see `docs/src/explanation/terragrunt-units.md`), not hardcoded in resource blocks — when adding a new add-on or resource with a version string or environment-specific setting, variablize it the same way rather than hardcoding it "for now."

## Physical & network topology

- **Compute**: 3 physical Proxmox nodes (`pve-node-0/1/2`) in a hyperconverged cluster (`homelab`) using Ceph for storage (`ceph-1` datastore).
- **Storage**: 1 NFS NAS for service data (Immich, etc.). Not yet under IaC management — provisioned/configured manually today. Revisit if it should be brought into Tofu or get its own IaC story.
- **Network**: Unifi-managed, one VLAN per cluster. Prod lives on VLAN 1601, subnet `192.168.160.0/27` (the range dev originally occupied, expanded from a `/28` once that filled up — see issue #3), gateway `192.168.160.1`; dev lives on VLAN 1602, subnet `192.168.160.32/27`, gateway `192.168.160.33` (see the `network` unit, `tofu/modules/network/main.tf`, and each environment's `env.hcl`). Every ingress hostname/OIDC redirect URI across every unit is driven by one per-environment `domain_name` value in `env.hcl` (dev: `dev.thepugh.family`; prod: the real `thepugh.family` apex — see #10). Local DNS resolution for that whole suffix is a Tofu-managed wildcard record (`unifi_dns_record.wildcard_ingress`, same `network` unit) pointed at a static `ingress_ip` (also `env.hcl`) that `core-addons` pins ingress-nginx's LoadBalancer Service to — documented in `docs/src/explanation/dns-and-hostnames.md`.
- **Real external domain**: `thepugh.family`, managed in Cloudflare. cert-manager uses a Cloudflare API token (DNS Zone Edit scope) for ACME DNS-01 challenges — this is the one credential in this repo with blast radius outside the homelab.
- **Docs site's real external domain**: `zanylights.com` (specifically `zanylights.com/homelab/`) — a separate, unrelated custom domain GitHub Pages serves this repo's mdBook site from (see Documentation section below). Not Cloudflare/Tofu-managed; configured directly in the repo's GitHub Pages settings.

## Kubernetes cluster

- Talos Linux, provisioned as Proxmox VMs via the `siderolabs/talos` and `bpg/proxmox` Tofu providers.
- 6 nodes per environment: prod is `k8s-ctrl-00/01/02` (control plane) + `k8s-node-00/01/02` (worker); dev's carry a `-dev-` segment so the two environments' hostnames never collide (`k8s-dev-ctrl-00/01/02` / `k8s-dev-node-00/01/02`) — one of each role per Proxmox node, both environments sharing the same 3 physical hosts. See each environment's `env.hcl`.
- **Node sizing**: `env.hcl`'s `node_resources` object (control-plane vs. worker cores/memory), not hardcoded per-node — control planes stay at 4 vCPU/4GB (nothing schedules there, Talos taints them by default); workers are 8 vCPU/16GB, resized up from the original 4 vCPU/4GB after that ceiling forced Loki's `chunksCache` off entirely and would have made Immich's ML service risky. Physical hosts are 3× i9-12900H (14 cores/20 threads, 64GB RAM each) — running dev and prod at these sizes simultaneously is a deliberate bet on that headroom (see issue #21), worth revisiting if either cluster's real workload grows. Resizing workers only (never control planes) means etcd quorum is never at risk — verified live via a real one-worker-at-a-time cordon/drain/reboot cycle, not just a Tofu apply.
- Cluster name `dev` or `prod`; each has its own Talos-managed floating VIP shared across its 3 control planes (not any single node's address), so the control plane stays reachable if one control-plane node is down — `192.168.160.2` for prod, `192.168.160.34` for dev (each is the first address after its environment's gateway, with the rest of that cluster's nodes numbered consecutively after it).
- **Terragrunt units**: the Tofu config is seven independently-applied units (`tofu/modules/{network,talos-cluster,core-addons,backup,keycloak-infra,keycloak-realm,observability}/`, wired by `tofu/live/{dev,prod}/*/terragrunt.hcl`), not one flat root module. A from-scratch stand-up or full teardown is one command — `terragrunt run --all --non-interactive -- apply -auto-approve` (or `destroy`) from `tofu/live/dev/` — verified live via a real destroy-then-recreate of the entire dev environment. Detailed docs: `docs/src/explanation/terragrunt-units.md`.
- Bootstrap add-ons (the `core-addons` unit): MetalLB, ingress-nginx, cert-manager, csi-driver-nfs/StorageClass (default, general file storage), ceph-csi-rbd/StorageClass (opt-in, database/block-semantics-sensitive workloads — see the Ceph storage bullet below), ArgoCD (HA, exposed at `argocd.<domain_name>`). Cluster-level *config* objects that used to be applied by Tofu `terraform_data`/`local-exec` provisioners — the MetalLB `IPAddressPool`/`L2Advertisement` (LB pool ranges, one per environment — `apps/cluster-addons/overlays/<env>/env-values.yaml`) and the `letsencrypt-prod`/`letsencrypt-staging` cert-manager `ClusterIssuer`s — are GitOps-managed now instead; see the app-of-apps entry below.
- **Ceph-backed storage**: a second StorageClass (`ceph-rbd-<cluster_name>`, opt-in, not default) for databases and other block-semantics-sensitive workloads, where NFS's fsync/locking semantics are a real correctness risk — general file storage stays on the default NFS StorageClass. ceph-csi (RBD, external-cluster mode) connects directly to the existing Proxmox Ceph cluster (`ceph-1` datastore, already backing Talos VM disks) — no Ceph daemons run inside Kubernetes, no new hardware. A dedicated pool (Tofu-managed, `proxmox_ceph_pool` in the `talos-cluster` unit) keeps Kubernetes' Ceph credential scoped away from the pool VM disks use. The CephX credential itself is manually bootstrapped (Ceph's own auth system, not Proxmox's — no Tofu resource for it) and stored in `tofu/secrets.enc.yaml` like every other provider credential. See `docs/src/explanation/ceph-backed-storage.md`.
- **App-of-apps**: an ArgoCD `ApplicationSet` (part of the `core-addons` unit, `var.gitops` for repo/revision) auto-discovers one `Application` per `apps/<app>/overlays/<cluster_name>` directory, so adding a new app is "add `apps/<app>/base/` plus an `overlays/<env>/` per existing environment, push" — no Tofu change, no manual `kubectl`/`argocd` command. Every `apps/<app>/` directory (eight today: `cluster-addons` plus the seven real workloads below) is split into an environment-agnostic `base/` and a tiny per-environment `overlays/dev|prod/` (a small `ConfigMap` of real values + a `kustomization.yaml` `replacements:` block wiring them into `base/`'s placeholder tokens) — added specifically so `dev`/`prod` don't need two near-duplicate copies of each app's manifests for the handful of values (hostnames, StorageClass names) that actually differ. `apps/cluster-addons/` is the cluster-level-config directory mentioned above. Detailed docs: `docs/src/explanation/gitops-app-of-apps.md`.
- **Immich**: the first real app-of-apps workload (`apps/immich/`), reachable at `photos.<domain_name>` on the LAN/VPN (not currently public — see the Public ingress bullet below). Database on the Ceph-backed StorageClass (`tensorchord/vchord-postgres`, a purpose-built VectorChord image — not CloudNativePG, which is what immich-charts' own README recommends, to avoid a whole new operator/CRDs for one database), media library on the NFS-backed one. Auth via Keycloak's native OIDC support, same pattern as ArgoCD/Grafana. The chart itself is a pinned `helm template` render committed as static YAML (`apps/immich/immich.yaml`), not rendered live via Kustomize's `helmCharts:` — that combination has a real, currently-unresolved OCI-pulling bug (kubernetes-sigs/kustomize#4381). See `docs/src/explanation/immich.md`.
- **Five more self-hosted apps**: Actual Budget (`apps/actual/`), Paperless-ngx (`apps/paperless/`), Vaultwarden (`apps/vaultwarden/`), Homebox (`apps/inventory/`), and changedetection.io (`apps/changedetection/`) — all LAN/VPN-only like Immich, plain hand-rolled Kustomize manifests (no Helm charts) following Immich's storage-split pattern: SQLite/Postgres on the Ceph-backed StorageClass, bulk files (Paperless's document library) on the NFS-backed one. Four have native OIDC (Actual, Paperless-ngx, Vaultwarden, Homebox — Paperless-ngx additionally syncs `platform-admins` to Django superuser via its own group-claim support); changedetection.io has none, so it's the first *real* app to use the `oauth2-proxy` forward-auth template `sso-demo` exists to prove out. See `docs/src/explanation/self-hosted-apps.md`.
- **Homepage** (`apps/homepage/`, #59): a service-dashboard landing page (`gethomepage.dev`), deliberately the exception to every pattern above — no PVC at all (its config is plain YAML, mounted as a `ConfigMap`) and therefore no Velero coverage either, since there's no stateful data to protect. Native OIDC (v2.0+) same as four of the five apps above, but Homepage applies no claim-based authorization of its own — any Keycloak-authorized identity gets in, same access-gate reasoning as every other app here. Static, hand-authored `services.yaml` rather than Homepage's Kubernetes-auto-discovery mode, which would need a `ServiceAccount` with read access to the Kubernetes API — the first such access any app in this repo would have; skipped in favor of this repo's existing preference for explicit/reviewable config. LAN/VPN-only, permanently — never a candidate for `public_apps` (surfaces internal topology). See `docs/src/explanation/self-hosted-apps.md`'s Homepage section for two real deploy-time gotchas (kubelet's probes rejected by Homepage's own host-validation; the image crashing under `runAsNonRoot` trying to auto-populate config files it couldn't find).
- **Public ingress**: a Tofu-managed Cloudflare Tunnel (`core-addons`, new `cloudflare` provider) — outbound-only, no port-forward — gated entirely on `public_ingress_enabled` (`env.hcl`; `false` for dev, `true` for prod). **Only prod is meant to be publicly exposed long-term**: dev's exposure was a temporary proof of the mechanism (real end-to-end logins, real Cloudflare edge connections) and has since been torn down — the user has an existing Immich elsewhere at `photos.thepugh.family` to migrate to a legacy domain before prod claims that hostname, and prod's own `domain_name` being the bare apex avoids the hostname-split complexity dev's exposure surfaced. Ingress rules, when enabled, are an explicit allowlist (`env.hcl`'s `public_apps`): each entry forwards its full hostname, while Keycloak gets exactly one path-scoped route (`^/realms/homelab/.*`, gated by `public_keycloak_realm`) so its admin console stays internal/VPN-only by construction — not a denylist rule that could miss a path. `cloudflared` is hand-rolled (no official chart), 2 replicas using Cloudflare Tunnel's native multi-connector support. **Public hostnames live one level under the real apex** (`public_apex_domain` + `public_hostname_suffix`), not under `domain_name` — Cloudflare's free Universal SSL only covers one subdomain level, found live as a real `ERR_SSL_VERSION_OR_CYPHER_MISMATCH` on dev's public hostname; prod doesn't need the suffix at all, since its `domain_name` is already the apex. `cloudflared` rewrites the Host header back to the internal hostname when forwarding. See `docs/src/explanation/public-ingress.md`.
- **Backup**: Velero + MinIO (the `backup` unit), also Tofu/Helm-managed rather than GitOps — MinIO is an S3-compatible gateway in front of the NFS share (its own data volume is just another PVC on the `nfs_storage`-backed StorageClass), and Velero backs up Kubernetes object definitions to it on a daily schedule (`var.backup`). CSI volume snapshots stay disabled, but File System Backup (`deployNodeAgent = true`, Velero's kopia integration) is enabled for real Ceph-backed volume data, not just object definitions (NFS-backed data still doesn't strictly need this, since restoring the PV object alone reconnects to data the NAS's own offsite backup already protects, but File System Backup covers both StorageClasses uniformly rather than needing a second, Ceph-only mechanism like CSI snapshots). It's opt-in per-pod via the `backup.velero.io/backup-volumes: <volume-name>` annotation — **standing rule: every workload's Ceph-backed (`ceph-rbd-<cluster_name>`) data volume gets this annotation, no exceptions.** An audit found 4 of 7 self-hosted apps (Actual Budget, Vaultwarden, Homebox, changedetection.io) missing it despite holding real data there — fixed, see the History entry below. Apply this to any future Ceph-backed workload's pod spec as part of onboarding it, not as an afterthought. Required moving the `velero` namespace to `privileged` PSA (node-agent's DaemonSet needs real host-level volume-path access) and an explicit `HOME=/tmp` env var on the main Velero container (kopia's repo path resolves off `$HOME`, which is unset under a non-root `runAsUser` with no matching `/etc/passwd` entry — found live as a real `mkdir /udmrepo: permission denied` on the first backup attempt). Detailed docs, including the restore procedure: `docs/src/explanation/backup-and-restore.md`.
- **SSO**: Keycloak + a hand-rolled Postgres `StatefulSet` (the `keycloak-infra` unit), reachable at `keycloak.k8s.thepugh.family`. The `homelab` realm and its OIDC clients (the `keycloak-realm` unit) are managed declaratively via the `keycloak` Terraform provider — same pattern as `unifi_network.this` — authenticating with the same Tofu-generated bootstrap admin credentials Keycloak itself is given. Splitting Keycloak's bootstrap from its realm config into two Terragrunt units (rather than one `tofu/sso.tf`) is what eliminated the old `-target=time_sleep.wait_for_keycloak` two-phase bootstrap for good — see `docs/src/explanation/terragrunt-units.md`. An oauth2-proxy + `whoami` forward-auth demo at `sso-demo.k8s.thepugh.family` is a permanent reference deployment, not a throwaway — it's the copy-paste template for real apps that need forward-auth. ArgoCD and Grafana both authenticate via Keycloak's native OIDC support too (local admin disabled on both), gated on membership in a `platform-admins` Keycloak group rather than any hardcoded person's identity — real accounts and group membership are managed by hand in Keycloak's admin console, not in Tofu. See `docs/src/explanation/sso-and-keycloak.md`.
- **Observability**: kube-prometheus-stack (Prometheus + Alertmanager + Grafana + node-exporter + kube-state-metrics) plus Loki + Grafana Alloy for logs (the `observability` unit), all Tofu/Helm-managed. It depends on `core-addons` like `backup`/`keycloak-infra` do, but — since Grafana's OIDC client secret (#32) is generated here and consumed by `keycloak-realm` — `keycloak-realm` now depends on `observability` too, so it's no longer an unordered sibling of `keycloak-infra`/`keycloak-realm` in the DAG; it applies before both. Grafana is reachable at `grafana.k8s.thepugh.family`; default cluster/node dashboards and most baseline alerts (node down, PVC nearly full, etc.) come from the chart's own defaults for free. Alertmanager routes to a Discord webhook (`discord_alert_webhook` in `tofu/secrets.enc.yaml`). cert-manager certificate-expiry and Velero backup-staleness alerts are added via the chart's own `additionalPrometheusRulesMap`/`additionalScrapeConfigs` values rather than separate `ServiceMonitor`/`PrometheusRule` custom resources in `core-addons`/`backup` — those would need this unit's Prometheus Operator CRDs to exist before `core-addons`/`backup` apply, which is backwards in the DAG. Detailed docs: `docs/src/explanation/observability.md`.
- **NetworkPolicies + Pod Security Admission**: every namespace this repo manages is default-deny on ingress and egress, with explicit allow rules for the traffic it actually needs, plus an explicit PSA level (`restricted` where a chart supports it, `baseline` where a one-shot Helm hook Job doesn't expose enough of a `securityContext` to reach `restricted`, `privileged` only for the 3 namespaces with a genuine `hostNetwork`/`hostPID`/`hostPath` need — `metallb-system`, `csi-driver-nfs`, `monitoring`). Lives as `kubernetes_network_policy`/namespace-label resources directly in whichever unit already owns that namespace, referencing other namespaces by their automatic `kubernetes.io/metadata.name` label rather than any new Terragrunt `dependency` wiring. Detailed docs, including the specific chart-default gaps found live: `docs/src/explanation/network-policies.md`.
- **Remote Tofu state**: a plain `local` backend per unit, all rooted under `tofu/state/` — a gitignored directory meant to be an SMB mount of a NAS share, set up out-of-band (not Tofu-managed) — chosen specifically so state storage never depends on infrastructure this config itself creates/destroys (no "destroying your own state backend" risk on a full teardown) and without introducing a new external dependency (cloud object storage). Each unit's exact path is generated by `tofu/live/root.hcl`'s `remote_state` block from directory structure, not hand-typed. See `docs/src/explanation/remote-state.md` for the SMB mount setup.
- **Dev/prod separation**: both `tofu/live/dev/` and `tofu/live/prod/` are live, each the identical seven-unit shape with real (not placeholder) `env.hcl` values — separate VLANs, separate NFS exports, separate Ceph pools, separate state trees, nothing shared except the physical Proxmox/Ceph hardware underneath. See `docs/src/explanation/terragrunt-units.md`.

## Toolchain

Every CLI below is version-pinned and installed via **[mise](https://mise.jdx.dev/)** (`mise.toml` at the repo root) — install mise itself first, then `mise trust && mise install` from the repo root gets a fresh machine every tool in one step, at the exact versions this repo is verified against. Bumping a pin is a deliberate edit to `mise.toml` followed by `mise install`, the same "variablize it, don't hardcode a moving target" philosophy this repo already applies to Helm chart versions in `env.hcl`. `mise activate` in your shell rc (or `mise exec -- <cmd>` per-command) puts the pinned versions on `PATH`; run `mise doctor` if a command resolves to a different version than expected.

- **OpenTofu** (not Terraform) — `tofu` CLI. **Terragrunt** orchestrates it (see Kubernetes cluster section above) — config lives in `tofu/modules/` (plain Tofu root modules, one per unit) and `tofu/live/` (per-environment Terragrunt wiring); commands are run as `terragrunt ...` from a `tofu/live/<env>/<unit>/` directory (or `tofu/live/<env>/` for `run --all`), not `tofu ...` directly. Detailed docs: `docs/src/explanation/terragrunt-units.md`. State lives on an SMB-mounted NAS share — a fresh machine needs that share mounted at `tofu/state/` before running `terragrunt init`, or Tofu will happily create fresh empty local state files instead of finding the real ones.
- **sops** + **age** — secrets encryption, see below.
- **gh CLI** — authenticate as ZanyHunter over HTTPS after install (`gh auth login`; mise only manages the binary, not the auth session). Used for the branch/PR workflow (see Git workflow below).
- **mdBook** — pinned to v0.5+ (required for the `mdbook-tabs` preprocessor below, which targets mdBook 0.5's preprocessor protocol and fails to parse against 0.4.x). Docs source is `docs/src/`; the built site `docs/book/` is gitignored (not committed) — run `mdbook build docs` locally to preview, no need to commit output. **mdbook-tabs** (mise's `cargo:` backend, which is also why `rust` is pinned in `mise.toml` — mise builds it from crates.io using its own managed Rust toolchain, no separate `cargo install` step) adds the global Production/Development domain-suffix tab switcher used throughout `docs/src/guides/` and `docs/src/explanation/` — see `docs/book.toml`'s `[preprocessor.tabs]`. Its `{{#tabs}}`/`{{#tab}}` markup only works as a standalone top-level Markdown block, not nested inside a list item or inline mid-paragraph (confirmed live — both produce broken/unparsed output), so a tabbed hostname mention is deliberately pulled onto its own line rather than left inline in surrounding prose.
- **kubectl** — pinned in `mise.toml` close to (not necessarily identical to) the cluster's own Kubernetes version, per `kubectl`'s ±1-minor version-skew policy — check the actual server version (`kubectl version`) before bumping this pin far ahead of it. This session's Bash environment has confirmed LAN reachability to `192.168.160.0/27` (verified via `ping` to a control-plane node and the gateway, 2026-08-27) — don't assume otherwise. If `ping`/`kubectl` fail, check first rather than declaring an environment limitation: the cluster's CA/certs regenerate on every from-scratch rebuild, so a cached `~/.kube/config` from before a rebuild will fail TLS verification even though the network path is fine — fetch a current one with `terragrunt output -raw kube_config` (from `tofu/live/dev/talos-cluster/`) rather than assuming a stale kubeconfig is still valid. Since #44, `kubectl` is also a hard *automation* dependency, not just an interactive convenience: `core-addons`'s `null_resource.external_secrets_crds` shells out to it via a `local-exec` provisioner (building its own throwaway kubeconfig from Tofu-known connection details, not `~/.kube/config`) to apply ExternalSecrets Operator's CRDs outside Helm's own lifecycle — a `terragrunt apply` of that unit fails outright on a machine without `kubectl` on `PATH`.
- **velero CLI** — pinned in `mise.toml`, **must be kept in lockstep with `chart_versions.velero`** in `tofu/live/<env>/env.hcl`: that value pins the Helm chart, whose `Chart.yaml` `appVersion` is the matching CLI/server version (currently chart `12.1.0` → CLI/appVersion `1.18.1`, `mise.toml`'s current pin) — a mismatched CLI can still work day-to-day but isn't guaranteed compatible with the server. When bumping `chart_versions.velero`, bump `mise.toml`'s `velero` pin to match in the same change. See `docs/src/explanation/backup-and-restore.md`.

## Secrets management

Provider credentials (Proxmox, Unifi, Cloudflare) live encrypted at `tofu/secrets.enc.yaml`, committed to git. Encrypted with SOPS, recipient is a single age keypair.

- **Decryption**: Terraform reads the file automatically via the `carlpett/sops` provider at plan/apply time — no manual decrypt step needed for normal Tofu usage. Since the Terragrunt refactor, the actual `data "sops_file"` block is generated per-unit from `tofu/live/root.hcl`'s `secrets_tf` local, only into the units that need decrypted credentials (`network`, `talos-cluster`, `core-addons`, `observability`) — see `docs/src/explanation/terragrunt-units.md`.
- **Manual edit**: `sops tofu/secrets.enc.yaml` (opens decrypted in `$EDITOR`, re-encrypts on save).
- **The age private key** lives at `~/.config/sops/age/keys.txt` on this machine (mode 600) — that's the default lookup path for both `sops` and the Terraform provider. It is **not** in git and never should be.
- **Disaster recovery for the key itself**: the private key is backed up in the user's KeePass file, which is itself stored offsite separately from this repo. If this machine is lost, recover the key from KeePass and place it back at `~/.config/sops/age/keys.txt` before running `tofu` commands.
- **Design note**: this is a single age key covering all secrets (Proxmox, Unifi, Cloudflare) — an honor-system boundary, not a technical one. We considered splitting Unifi/Cloudflare into a separately-keyed file so Claude could be structurally prevented from touching them, and decided against it: the user has a fresh full Unifi backup, so the blast radius of an honor-system violation is a few minutes of restore time. Revisit this if that risk tolerance changes.
- **GitOps secrets (ksops)**: ArgoCD's repo-server also has this same age key, mounted as a `kubernetes_secret` in the `argocd` namespace (the `core-addons` unit, `tofu/modules/core-addons/main.tf`), so it can decrypt SOPS-encrypted manifests under `apps/` at sync time via [ksops](https://github.com/viaduct-ai/kustomize-sops). This means the raw private key now lives in one additional place beyond this machine + KeePass: as a live Kubernetes Secret in-cluster. Accepted for the same reason as the single-key design above (dev cluster, single operator); revisit alongside that note if the risk tolerance changes. See `docs/src/explanation/gitops-app-of-apps.md` for how to add a new encrypted secret this way.
- **Tofu-generated secrets consumed by GitOps apps (ExternalSecrets Operator, #42)**: ksops is for secrets with no other source of truth; it's the wrong tool for a value Tofu also independently generates (a Keycloak OIDC client's `client_secret`) and needs to keep matching, since a ksops-encrypted copy silently drifts the moment the Tofu side regenerates it (a `keycloak-realm` destroy/recreate, a deliberate rotation). [External Secrets Operator](https://external-secrets.io/) (`helm_release.external_secrets`, `core-addons`) closes this gap for exactly that subset — no Vault, no new secrets-store service, it just mirrors a Kubernetes Secret Tofu writes into a `keycloak-secrets` namespace (owned by `core-addons`, populated by `keycloak-realm` — split this way since #44, so the namespace reliably exists before ArgoCD's first sync of the RBAC targeting it) out into each real app's own namespace. Its own access surface is deliberately narrow: the RBAC backing its `ClusterSecretStore` (`apps/cluster-addons/base/`, GitOps-managed) grants read-only access to Secrets in the `keycloak-secrets` namespace and nowhere else — no access to `tofu/secrets.enc.yaml`, no access to any other namespace's Secrets. See `docs/src/explanation/gitops-app-of-apps.md`'s ExternalSecrets section.

## Standing permissions & guardrails

- **Proxmox and Kubernetes (dev cluster)**: full autonomy. Run `terragrunt`/`tofu plan`/`apply`/`destroy`, `kubectl`, `helm` freely against this stack without asking first — it's dev-only and disposable.
- **Proxmox and Kubernetes (prod cluster)**: the opposite of dev — prod is real and in active use, so the user is intentionally the only one running Tofu against it. Enforced technically, not just by instruction: a project-level `.claude/settings.json` deny rule (`Bash(*tofu/live/prod*)`) blocks any `terragrunt`/`tofu` command referencing `tofu/live/prod/` outright — verified live to block both `cd`-based and `--terragrunt-working-dir`-based invocations with no prompt shown, while leaving `tofu/live/dev/` unaffected. This is a first, cheap layer (pattern-matched, not a hard stop); a per-environment sops/age key split (so prod's secrets can't be decrypted from this machine at all) is the planned follow-up for a real cryptographic barrier, not yet implemented.
- **Unifi**: do **not** author or apply changes to Unifi-managed Tofu resources (currently `unifi_network.this`, in the `network` unit, and the `unifi` provider block) that change what's actually deployed — new Unifi resources, address space changes, or any other config change — without asking the user first. It does **not** mean avoiding the files entirely: read-only operations (`tofu plan`) and mechanical formatting (`tofu fmt` and similar tools) are fine even if they happen to touch a line inside a Unifi resource block, since those don't change intent or behavior. **Exception, explicitly authorized**: each cluster (dev today, a future prod) has exactly one Unifi VLAN tied to that cluster's own lifecycle — standing it up or tearing it down as part of a normal cluster destroy/recreate cycle is pre-approved and needs no per-instance sign-off or `-target` workaround, as long as its configuration doesn't change in the process.
- **Cloudflare/DNS**: same ask-first treatment as Unifi. The token controls a real domain; cert-manager's existing use of it (DNS-01 challenges) is already approved and needs no further confirmation, but any new Cloudflare-related Tofu resource or config change should be proposed and confirmed before applying.
- **Everything else** (docs, non-secret Tofu resources, CI config, etc.): normal judgment — no special standing restriction beyond the git workflow below.

## Git workflow

- **Commit messages**: Conventional Commits, always (`feat:`, `fix:`, `docs:`, `chore:`, etc., with a scope where it adds clarity, e.g. `feat(tofu): ...`). Split unrelated concerns into separate, self-consistent commits rather than one large commit — each commit should leave the repo in a valid state.
- **Two-stage promotion pipeline** (#51): a persistent `development` branch sits between a feature branch and `main`. Day-to-day work targets `development`, not `main` — `feature branch → PR → development`. `development` is what dev's ArgoCD `ApplicationSet` tracks (`gitops.revision` in `tofu/live/dev/env.hcl`), so merging there is what actually deploys a change to the dev cluster. Once it's validated live on dev, a second PR promotes it — `development → PR → main` — which is what prod's ArgoCD tracks (`tofu/live/prod/env.hcl`, unchanged at `"main"`). Never push directly to either branch; both are protected by real GitHub rulesets (not just this instruction) requiring a PR to merge. This applies to Tofu module/`env.hcl` changes too, not just `apps/`: even though `terragrunt apply` isn't driven by any tracked git ref (it just runs against whatever's checked out locally), the convention is the same two-stage flow — apply and verify a Tofu change from a `development`-bound branch on dev first, then open the promotion PR before it's ever applied to prod. This is a workflow discipline, not a technical gate the way `gitops.revision` is for ArgoCD-managed apps — nothing stops a `terragrunt apply` run out of sequence, so follow it deliberately.
- **Branch naming**: `type/short-description` (e.g. `feat/argocd-app-of-apps`, `docs/dns-guide`), mirroring the commit type. Base every feature branch off `development`, not `main`.
- Open PRs with `gh pr create`. Wait for the user to review and merge — do not merge PRs unilaterally, at either promotion stage.

## Tasking workflow

How the user hands off work, especially for larger refactors/features tracked over multiple sessions:

- **GitHub Issues are the backlog.** One issue per larger refactor or feature, with a checklist of subtasks in the body. Claude Code does not retain memory across sessions by default, so an issue is durable state a future session can re-read cold — treat it as more reliable than chat history for "what are we doing and why."
- **No passive awareness.** Claude does not see new GitHub comments, issues, or PR activity as they happen — only when a session actively runs a `gh` command. Nothing happens automatically just because something was posted on GitHub.
- **To task Claude**: point it at the issue number in a live session (e.g. "pick up #4"). It should pull the issue via `gh issue view`, do the work with full local access (secrets, LAN, everything this environment has), open a PR against `development` per the Git workflow above, and comment back on the issue linking the PR (or close it once both the `development` and the follow-up `main` promotion PRs have merged).
- **The `@claude` GitHub App/Action integration** (triggers an automated run when `@claude` is mentioned in an issue/PR, no local session needed) was considered and deliberately skipped for now: that integration runs on an isolated GitHub Actions runner with access only to the git repo and configured Actions secrets — no local machine access, meaning no age key and no LAN reachability. Since nearly everything in this repo eventually touches secrets or needs LAN access, it would only cover a narrow slice of work (pure code review/refactor suggestions). Revisit if the balance of work shifts toward tasks that don't need local access.
- **GitHub Projects** (kanban board over issues) is worth adding once more than 3-4 larger initiatives are in flight concurrently; not needed yet.

## Documentation

Keep `docs/src/` in sync with infrastructure changes as part of the same change/PR — when a Tofu change alters operational procedure or adds/changes a subsystem, update the relevant mdBook page(s) alongside it rather than letting docs drift.

**Structure**: the site follows the [Diátaxis](https://diataxis.fr/) framework, four root sections under `docs/src/`. **`guides/`** is task-oriented how-tos (standing up the environment from scratch, onboarding a new app, restoring a backup) — a new subsystem's own architecture/reasoning does **not** belong here; add a short step or a link out instead. **`explanation/`** is where a new subsystem's "why" writeup and any real gotchas found deploying it actually belong — one page per subsystem, unnumbered, ordered roughly infra → add-ons → GitOps/apps → operational concerns. **`reference/`** is dry factual lookups (directory layouts, exact settings, hostname tables) — extend an existing table (e.g. `reference/deployed-apps.md`) rather than writing prose. **`tutorials/`** is a deliberate stub (see its index page) — this is a single-operator homelab, not an onboarding funnel; leave it alone unless the user asks otherwise.

**Publishing** (`.github/workflows/docs.yml`): builds and deploys via a `gh-pages` branch (GitHub Pages source is "Deploy from a branch", not the Actions-artifact deployment type — needed so production and PR previews can coexist as separate subdirectories of the same branch without one wiping the other). A push to `main` deploys to the branch root (`peaceiris/actions-gh-pages`, `keep_files: true`); every PR gets its own live preview at `zanylights.com/homelab/pr-preview/pr-<N>/` (`rossjrw/pr-preview-action`), GitLab "View app"-style — the action posts/updates a sticky PR comment with the link and automatically removes the preview directory when the PR closes, no separate cleanup job needed.

## History / key decisions

This section is deliberately pruned to durable decisions and gotchas that could recur — the full "why" and step-by-step verification for anything with a live `docs/src/explanation/` page lives there instead, per the Documentation section above.

- Chose SOPS + age over a NAS-hosted secrets store (e.g. Vault) specifically so secrets survive a NAS-down disaster — encrypted secrets committed to git means any clone has the ciphertext, and only the age key (KeePass-backed, offsite) is the recovery-critical piece.
- Bootstrapped the ArgoCD app-of-apps ApplicationSet and wired ksops into the repo-server for GitOps-managed secrets (closed issues #6, #7), migrating the MetalLB pool and cert-manager `ClusterIssuer`s off Tofu `terraform_data`/`local-exec` in the process. Chose ksops over External Secrets Operator/Vault at the time specifically to avoid running a new component, extending the same age-key pattern `secrets.enc.yaml` already used — a decision later narrowly revisited for Tofu-generated secrets specifically (see the ExternalSecrets entry below).
- Deployed Velero + MinIO for cluster backups (closed issue #8) — MinIO because Velero needs an S3 API and doesn't speak NFS natively. Verified with a real backup → delete-namespace → restore round-trip, not just a `Completed` status.
- Deployed Keycloak + Postgres for SSO (closed issue #9): realm/clients managed via the `keycloak` Terraform provider (same declarative-provider pattern as `unifi_network.this`), Postgres a hand-rolled `StatefulSet` rather than a chart for the same pinned-version reasoning as MinIO. Verified with a real end-to-end OIDC login, not just "the client exists."
- Moved Tofu state off local-only storage (closed issue #12). First attempt was a remote S3 backend on MinIO — worked, including OpenTofu's native S3 conditional-write locking — but was reverted: MinIO is created *by* this Tofu config, so destroying the cluster would eventually destroy the very thing backing its own state. Replaced with a plain `local` backend on an SMB-mounted NAS share, which depends on nothing this config itself creates or destroys. Also surfaced that backend blocks can't reference variables (a hardcoded literal location) — what prompted adopting Terragrunt (below).
- Adopted Terragrunt, splitting the monolithic root module into independently-applied units (closed issues #21, #26) — see `docs/src/explanation/terragrunt-units.md`. Fixes the Keycloak two-phase bootstrap for good (`dependency` blocks, not `-target`, enforce ordering) and gives real dev/prod separation. Verified with a real full destroy-then-recreate of dev, which caught three bugs worth remembering: `helm_release.ingress_nginx` needs `wait = false` (its default wait-for-LoadBalancer-IP deadlocks on a from-scratch bootstrap, since MetalLB's `IPAddressPool` is GitOps-managed and can't exist until ArgoCD has synced); every `dependency` block's `mock_outputs_allowed_terraform_commands` needs `"destroy"` added (without it, `run --all destroy` can't clean up a partially-applied stack); and oauth2-proxy's Ingress needs `nginx.ingress.kubernetes.io/proxy-buffer-size: "16k"` (Keycloak's bundled tokens exceed ingress-nginx's default buffer, 502ing every login).
- Deployed kube-prometheus-stack + Loki/Alloy for logs (closed issue #14) — a seventh Terragrunt unit. Alertmanager routes to Discord; verified with a synthetic alert confirmed to actually arrive, not just a healthy-pods check. Two Talos incompatibilities worth remembering: kube-prometheus-stack's default `kube-proxy`/`kube-scheduler`/`kube-controller-manager` scrape jobs assume kubeadm-style host-network exposure Talos doesn't provide (permanent `TargetDown` until disabled); and Loki's `chunksCache` defaults to ~8Gi, more than a node had at the time — fixed properly later by resizing workers rather than leaving it disabled forever (see the Node sizing bullet above).
- Rolled out default-deny NetworkPolicies and an audited Pod Security Admission level across every managed namespace (closed issue #31). Applied one namespace group at a time, re-verifying every previously-established bar (Velero backup, Keycloak login, alerting, ArgoCD sync, PVC provisioning) after each rollout. Gotchas worth remembering for any new namespace: an `allow-same-namespace` policy needs to be unconditional, not judged pod-by-pod (a default-deny rollout without one silently hung MinIO's own bucket-creation Job); check an existing data directory's real uid against a throwaway debug pod before assuming one (Postgres's was 70, not the 999 first guessed); and a StatefulSet controller can leave a crash-looping pod running under its *old* spec for several minutes after a fix, needing a manual pod delete.
- Wired ArgoCD and Grafana into Keycloak SSO via native OIDC, disabling local admin on both (closed issue #32) — RBAC is group-based (`platform-admins`) rather than tied to any hardcoded identity, at the user's explicit request. Gotcha worth remembering: ArgoCD's chart default `configs.cm.url` (`https://argocd.example.com`) is what it actually uses to build its OIDC `redirect_uri`, not the incoming request's `Host` header — left unset, every real login gets rejected as an invalid redirect URL.

Deliberately a single Tofu-managed wildcard DNS record rather than ExternalDNS or per-hostname records; both would add a component/maintenance burden the wildcard already avoids for free.
