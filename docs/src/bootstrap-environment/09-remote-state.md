# 10. Remote Tofu State

Tofu's state now lives remotely, in the same [MinIO](https://min.io/) instance stood up for Velero backups (`tofu/backup.tf`) — a dedicated `tofu-state` bucket, separate from Velero's own `velero` bucket. This replaces the previous local-only `tofu/terraform.tfstate`, which was a real single point of failure (losing this machine meant losing the state file, with no locking to protect against two concurrent `tofu apply` runs either).

MinIO's S3 API is exposed via an Ingress (`tofu/state-backend.tf`) at `minio.k8s.thepugh.family` — reachable from any device on the internal network, resolved by the same wildcard DNS record already covering `*.k8s.thepugh.family` (see [DNS Configuration](./04-dns-configuration.md)), so no new Unifi change was needed. Only the S3 API port (9000) is exposed; the admin console (9001) is not.

---

## One-time setup on a new machine

1. Get the MinIO root credentials from the live cluster:
   ```bash
   kubectl get secret minio-credentials -n minio -o go-template='{{.data.rootUser | base64decode}}'
   kubectl get secret minio-credentials -n minio -o go-template='{{.data.rootPassword | base64decode}}'
   ```
2. Copy `tofu/backend.hcl.example` to `tofu/backend.hcl` (gitignored — never commit this file) and fill in `access_key`/`secret_key` with the values above.
3. Run:
   ```bash
   tofu init -backend-config=backend.hcl
   ```

Steps 1-2 are the reason these credentials aren't sourced from `tofu/secrets.enc.yaml` like the Proxmox/Unifi/Cloudflare credentials are: they're generated by Tofu itself (`random_password.minio_root_password`) and only exist in state — but state is exactly what a backend config is needed to reach in the first place. Retrieving them from the live cluster directly sidesteps that circularity, the same way `tofu output -raw kube_config` is already the documented way to reconnect a fresh machine to the cluster (see `CLAUDE.md`'s Toolchain section) rather than assuming a copy of the kubeconfig survived.

## Why the backend can't be fully declarative

OpenTofu evaluates a `backend` block before any variables or resources are known, so it can't reference `var.tofu_state_bucket`, `var.cluster.name`, or anything else from this config — every value in the `backend "s3"` block in `tofu/terraform.tf` is a hardcoded literal, including the bucket name and the `dev/terraform.tfstate` key. A real multi-environment setup (prod, alongside dev) will need to confront this properly rather than hand-editing the literal — tracked as part of [#26](https://github.com/ZanyHunter/homelab/issues/26) (Terragrunt), which manages per-environment backend config as a generated file rather than a hand-maintained literal.

## Locking

The backend uses OpenTofu's native S3 conditional-write locking (`use_lockfile = true`, no DynamoDB-style lock table needed) — MinIO's deployed version (`RELEASE.2024-12-18T13-15-44Z`, from `chart_versions.minio`) supports the conditional `PutObject` semantics this requires. Verified with a real test, not just "the option is set": two `tofu plan` runs launched concurrently — the first acquired the lock and ran to completion, the second failed immediately with an S3 `412 PreconditionFailed` and a `Lock Info` block naming the first run.

## Bootstrapping a fresh cluster from scratch

This is the same category of chicken-and-egg problem documented for Keycloak in the [SSO](./08-sso.md) page: MinIO is itself created *by* this Tofu config, so a truly from-scratch rebuild (new hardware, empty state) can't point at the remote backend before MinIO exists yet. The sequence is:

1. Comment out (or delete) the `backend "s3"` block in `tofu/terraform.tf`, or run `tofu init -reconfigure -backend=false` to fall back to local state temporarily.
2. `tofu apply` normally — this creates the cluster, MinIO, and the `tofu-state` bucket, using local state.
3. Restore the `backend "s3"` block, get the root credentials (see above), and run `tofu init -backend-config=backend.hcl -migrate-state` to move the now-populated local state into the freshly created bucket.

Every apply after that is a normal `tofu apply` against the remote backend — this dance is only needed once, on a true from-empty-state rebuild.
