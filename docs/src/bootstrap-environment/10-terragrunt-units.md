# 11. Terragrunt Units and Multi-Environment Layout

`tofu/` used to be one flat root module — one state file, one environment ("dev"), no way to stand up a second cluster without clobbering the first. It's now six independently-applied [Terragrunt](https://terragrunt.gruntwork.io/) units, each its own Tofu root module, wired together by `dependency` blocks that read a prior unit's *already-applied* outputs.

---

## Layout

```
tofu/
  modules/                 # plain Tofu root modules — the actual resources
    network/                 # unifi_network.this (the VLAN)
    talos-cluster/            # Proxmox VMs, Talos bootstrap, kubeconfig
    core-addons/              # MetalLB, ingress-nginx, cert-manager, ArgoCD, NFS storage
    backup/                   # MinIO, Velero
    keycloak-infra/            # Postgres, Keycloak
    keycloak-realm/            # homelab realm/clients, oauth2-proxy + whoami demo
  live/
    root.hcl                 # shared: generates each unit's backend, secrets decrypt
    dev/
      env.hcl                  # this environment's real values (cluster, nodes, chart versions, ...)
      network/terragrunt.hcl
      talos-cluster/terragrunt.hcl
      core-addons/terragrunt.hcl
      backup/terragrunt.hcl
      keycloak-infra/terragrunt.hcl
      keycloak-realm/terragrunt.hcl
    prod/                     # same shape, placeholder env.hcl — scaffolding, never applied
      ...
```

Dependency graph: `network` → `talos-cluster` → `core-addons` → {`backup`, `keycloak-infra`} → `keycloak-realm`.

## Why units, not one module

Two concrete problems this solves:

1. **The Keycloak two-phase bootstrap.** The `keycloak` provider authenticates with an admin password generated in the same apply — a value that's unknown on a from-empty-state plan, which the old flat module couldn't resolve without a manual `tofu apply -target=time_sleep.wait_for_keycloak` first. Splitting `keycloak-infra` (creates the password) from `keycloak-realm` (uses it) into separate units fixes this structurally: `keycloak-realm`'s `dependency` block on `keycloak-infra` sets `mock_outputs_allowed_terraform_commands = ["init", "validate", "plan"]` — **not** `"apply"` — so `terragrunt run --all apply` refuses to synthesize a fake password at apply time. It blocks until `keycloak-infra` has genuinely finished applying and produced a real, known password, then generates the `keycloak` provider block with that literal value. No targeting, no bootstrap incantation to remember.
2. **Real dev/prod separation.** Each environment under `tofu/live/` is just another directory of the same six units, with its own `env.hcl` and its own generated state paths (see [Remote Tofu State](./09-remote-state.md)) — nothing shared, nothing to clobber.

## Day-to-day commands

From `tofu/live/dev/` (or any environment directory):

```bash
# Everything, in dependency order, one command:
terragrunt run --all --non-interactive -- apply -auto-approve

# Same, in reverse order, for a full teardown:
terragrunt run --all --non-interactive -- destroy -auto-approve

# Just one unit:
cd core-addons && terragrunt apply
```

`--non-interactive` skips the per-unit confirmation prompt `run --all` would otherwise show; `-auto-approve` is the underlying `tofu apply`'s own flag, passed through after the `--`. Terragrunt's own flags go *before* the `--`; anything after it goes to the wrapped `tofu` command — getting this backwards is a real footgun (`--non-interactive` after `--` gets silently ignored and you'll hit an interactive prompt in a non-interactive script).

## How units talk to each other

- **State**: each unit gets its own file, generated by `tofu/live/root.hcl`'s `remote_state` block — see [Remote Tofu State](./09-remote-state.md).
- **Providers**: each unit's `terragrunt.hcl` has a `generate "provider"` block. Units needing cluster access (everything past `talos-cluster`) build their `kubernetes`/`helm` provider config from `dependency.talos_cluster.outputs.kubernetes_client_configuration` — the same attributes a single `providers.tf` used to read directly off `talos_cluster_kubeconfig.this` before the split. `keycloak-realm` additionally builds a `keycloak` provider from `dependency.keycloak_infra.outputs.admin_password`.
- **Secrets**: `tofu/secrets.enc.yaml` (unchanged location/mechanism) is decrypted via a `generate "secrets"` block, but only into the units that actually need Proxmox/Unifi/Cloudflare credentials — `network`, `talos-cluster`, and `core-addons`. `backup`, `keycloak-infra`, and `keycloak-realm` never get it, so their state can never contain those credentials.
- **A real dependency, not just ordering**: `talos-cluster` reads its VLAN ID from `dependency.network.outputs.vlan_id` rather than a separately-supplied variable — the old flat module had a `# depends_on = [unifi_network.this]` that was commented out and never enforced anything. Now there's one source of truth.

## Adding a real prod environment

`tofu/live/prod/` already has the full six-unit shape with placeholder values in `env.hcl` — nobody has run `terragrunt apply` there. Before that's a real thing:

- Pick a real, unallocated VLAN ID and subnet (a Unifi change — needs sign-off per `CLAUDE.md`, and answers the still-open question from issue #21 about whether prod gets its own VLAN — it does, one VLAN per cluster, same as dev).
- Pick unallocated `vm_id`/IP ranges that don't collide with dev's.
- Provision a dedicated NFS export on the NAS (`CLAUDE.md`: "dev/prod will not share infrastructure").
- Decide the ingress hostname scheme — every hostname in `core-addons`/`keycloak-infra`/`keycloak-realm` is still a hardcoded literal (`argocd.k8s.thepugh.family`, etc.), not derived from an environment variable. Two environments live simultaneously would collide on these today; resolving that is unstarted follow-up work, not solved by this refactor.

## A caution learned from testing this live

Terragrunt's `dependency` blocks make a from-scratch `run --all apply` genuinely one command — verified with a real full destroy-then-recreate of the entire dev environment, not just a read of the docs. But "one command" doesn't mean "immune to real-world flakiness": a from-scratch run hit both a transient DNS failure resolving `factory.talos.dev` from the Proxmox host, and Talos VMs that were unusually slow to become network-reachable — neither caused by this refactor, both resolved by simply re-running the same `apply` command (already-applied resources are untouched; only what didn't finish gets retried). One real bug *was* found and fixed in the process: see `helm_release.ingress_nginx`'s `wait = false` in `tofu/modules/core-addons/main.tf` — Helm's default wait behavior blocked on a LoadBalancer IP that can only appear after ArgoCD (which depends on ingress-nginx) has synced the MetalLB pool, a genuine bootstrap-ordering circularity that never surfaced before because every prior apply was incremental against an already-assigned IP.
