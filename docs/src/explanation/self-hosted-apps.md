# Self-Hosted Apps: Actual Budget, Paperless-ngx, Vaultwarden, Homebox, changedetection.io, Homepage, Vikunja, Mealie, LubeLogger, Pinchflat

Ten more real workloads under `apps/`. The first five, plus Vikunja (#58), Mealie (#56), and LubeLogger (#55), follow [Immich](./immich.md)'s pattern: one `apps/<app>/` directory each, storage split by locking-sensitivity (Ceph-backed for anything SQLite/Postgres, NFS-backed for bulk files), and Keycloak SSO wherever the app supports it. Homepage (#59, its own section near the end of this page) is the deliberate exception — a stateless dashboard with no PVC and no Velero coverage at all. Pinchflat (#54, also its own section) breaks a second pattern: it's the first app in this repo whose core purpose needs real internet egress. See [Deployed Apps](../reference/deployed-apps.md) for the hostname table.

None of these are public — same LAN/VPN-only posture Immich started at, before public exposure was scoped to prod-only (see [Public Ingress](./public-ingress.md)). Homepage specifically should stay LAN/VPN-only permanently: a dashboard surfacing live status/links for every other internal app is exactly the kind of internal-topology information that shouldn't go to the public internet. Pinchflat's LAN/VPN-only posture isn't necessarily permanent the same way — it's the default per #54's own scope, with a specific, revisitable exception (wanting a podcast app to pull the RSS feed off-LAN) called out in its own section below.

---

## Storage

Every app here persists to either SQLite or Postgres except changedetection.io (JSON-based watch/history files) — all nine land on the Ceph-backed `ceph-rbd-dev` StorageClass rather than NFS, for the same fsync/locking-correctness reasoning as Immich's and Keycloak's Postgres (see [Ceph-Backed Storage](./ceph-backed-storage.md)). Paperless-ngx and Pinchflat are the two exceptions with a *second* PVC: their bulk file storage (Paperless's document library; Pinchflat's downloaded videos) has no locking-sensitivity, so it's on `nfs-dev`, split the same way Immich splits database vs. media.

| App | Database | Storage |
| --- | --- | --- |
| Actual Budget | SQLite (bundled) | 5Gi, `ceph-rbd-dev` |
| Paperless-ngx | Postgres (hand-rolled `postgres:16-alpine`, uid 70 — same image/uid as Keycloak's Postgres) | DB: 10Gi `ceph-rbd-dev`. Media: 100Gi `nfs-dev` |
| Vaultwarden | SQLite (bundled) | 5Gi, `ceph-rbd-dev` |
| Homebox | SQLite (bundled) | 2Gi, `ceph-rbd-dev` |
| changedetection.io | None — flat JSON datastore | 5Gi, `ceph-rbd-dev` |
| Vikunja | Postgres (hand-rolled `postgres:16-alpine`, uid 70 — same image/uid as Paperless-ngx's/Keycloak's Postgres) | DB: 5Gi `ceph-rbd-dev`. Attachments: 2Gi `ceph-rbd-dev` |
| Mealie | SQLite (bundled) | 5Gi, `ceph-rbd-dev` — DB and recipe images combined, no second PVC |
| LubeLogger | SQLite (bundled) | 5Gi, `ceph-rbd-dev` — DB and uploaded receipts/documents combined, no second PVC |
| Pinchflat | SQLite (bundled) | Config/DB: 5Gi `ceph-rbd-dev`. Downloads: 20Gi `nfs-dev` (prod: 500Gi) |

Vikunja is the second app here to choose Postgres over its own bundled SQLite option (#58) — a deliberate call, not a default: SQLite would have matched Actual/Homebox's precedent and been fine at household scale, but Vikunja's own docs recommend Postgres for real concurrent multi-user access, and there's no meaningful extra operational cost to following that recommendation given the hand-rolled Postgres pattern Paperless-ngx already established. Attachments (likely modest, unlike Paperless's document library) live on their own small Ceph-backed PVC alongside the database, both mounted by separate resources (a `StatefulSet` for Postgres, a `Deployment` for Vikunja itself).

Mealie (#56) goes the other way — SQLite over its own optional Postgres support, matching Actual/Vaultwarden/Homebox's precedent rather than Vikunja/Paperless-ngx's, since Mealie's own DB+image tree has no documented way to split apart and a household recipe library is unlikely to ever approach concurrent-writer territory. Its data directory (`/app/data`) holds the SQLite file and every recipe image together, so one PVC covers both rather than needing Immich/Paperless's DB-vs-media split.

Mealie's upstream image runs as root by default and its entrypoint uses `gosu` to chown `/app` and drop to a `PUID`/`PGID` (default 911, both confirmed against the image's own `docker/entry.sh`) — the same shape Homebox's original (non-fork) image had, which needed switching to a `-rootless` tag to satisfy `restricted` PSA. Mealie ships no such variant, but its entrypoint's root-required chown/`gosu` step only runs when the container actually starts as uid 0; setting `runAsUser`/`runAsGroup`/`fsGroup: 911` directly (911 already being the image's own default target uid) skips that branch entirely and starts the app straight as its intended non-root user — confirmed live on first deploy, no crash loop or permission error, no rootless variant needed.

LubeLogger (#55) also stores its SQLite DB and every uploaded receipt/document under one undividable `/App/data` tree, same combined-PVC shape as Actual/Mealie. Unlike Mealie, its base image (`mcr.microsoft.com/dotnet/aspnet:10.0`) ships no non-root user or `gosu`-style entrypoint at all — confirmed against its `Dockerfile` on GitHub, which has no `USER` directive — so `runAsUser`/`runAsGroup`/`fsGroup: 1000` is an arbitrary uid rather than one the image itself designates, safe here because Kubernetes chowns the freshly-provisioned Ceph PVC to that uid via `fsGroup` on mount, the same reasoning already established for Immich.

Pinchflat (#54) splits storage the same way Paperless-ngx does — its own internal SQLite DB (channel/playlist subscriptions, download history) under `/config` on the Ceph-backed StorageClass, downloaded video files under `/downloads` on the NFS-backed one — rather than combining them the way Actual/Mealie/LubeLogger do, since Pinchflat's config and media directories are genuinely separate mount points, not one shared tree. Its base image (`ghcr.io/kieraneglin/pinchflat`) has no built-in non-root user either, same situation as LubeLogger's — confirmed against its Dockerfile on GitHub (no `USER` directive) — so `runAsUser`/`runAsGroup`/`fsGroup: 1000` is again an arbitrary uid, safe for the same `fsGroup`-chowns-the-PVC-on-mount reason. Pinchflat's own entrypoint (`rel/overlays/bin/check_file_permissions`) actively verifies both mount points are writable by whatever uid it's running as before starting, and fails fast with a legible error if not — confirmed live with a clean `Running`/`Ready` pod on the first attempt, no crash loop needed to find the right uid.

Paperless-ngx also needs a Redis-compatible broker (task queue + websocket backend) regardless of DB choice — `paperless-redis` is the chart-free, hand-rolled Valkey image already used nowhere else in this repo, ephemeral (`emptyDir`, no PVC): losing the broker on a restart just means in-flight tasks re-run, no durable data lives there. Vikunja also supports an optional Redis-backed cache, but it's deliberately left disabled (#58) — unlike Paperless's Redis dependency above, Vikunja's is purely an optional performance optimization, unnecessary at household scale and not worth adding a new component for.

All nine Deployments/StatefulSets use an explicit `strategy: { type: Recreate }` (or, for Paperless's and Vikunja's Postgres, the StatefulSet default) — every Ceph-backed PVC here is `ReadWriteOnce`, so a default rolling update would try to schedule the replacement pod before the old one releases the volume and deadlock on a multi-attach error.

## A real gotcha found live: Kubernetes' auto-injected service-links env vars

Actual Budget's server crashed on first deploy with:

```
Error: port: ports must be within range 0 - 65535
```

Root cause: Kubernetes auto-injects Docker-links-style `<SVCNAME>_PORT`/`<SVCNAME>_SERVICE_*` env vars into every pod in a namespace, for every Service that namespace has, unless `enableServiceLinks: false` is set on the pod spec. The `actual` Service triggers an auto-injected `ACTUAL_PORT=tcp://<cluster-ip>:5006` — a URI string — which collides with Actual's *own* `ACTUAL_PORT` config key (convict's `port` format expects a bare integer). The app never had a chance to read its intended default; it read Kubernetes' injected value instead, got `NaN`, and failed range validation.

Paperless-ngx carries the same risk for the identical reason: its own internal listen-port setting is *also* named `PAPERLESS_PORT`, and its Service is also named `paperless` — the exact same collision shape, just not yet triggered at deploy time. Rather than fix only the app that actually broke, `enableServiceLinks: false` is set on every pod spec across all five apps in this batch — none of them rely on legacy Docker-links-style service discovery (they all use real Kubernetes DNS names like `paperless-postgres`, `paperless-redis` directly in config), so there's no downside to disabling it everywhere.

## Authentication

### Native OIDC: Actual Budget, Paperless-ngx, Vaultwarden, Homebox, Vikunja, Mealie, LubeLogger

All seven support Keycloak login directly — no oauth2-proxy needed, same pattern as Immich/ArgoCD/Grafana. Each has its own `keycloak_openid_client` in `tofu/modules/keycloak-realm/main.tf`, secret Tofu-generated and synced automatically into that app's namespace via ExternalSecrets Operator (#42), following the [Onboard a New App](../guides/onboard-a-new-app.md) guide's "apps with native OIDC support" path and [GitOps: App-of-Apps and Secrets](./gitops-app-of-apps.md)'s ExternalSecrets section.

- **Actual Budget**: `ACTUAL_OPENID_*` env vars (`ACTUAL_LOGIN_METHOD=openid`, `ACTUAL_ALLOWED_LOGIN_METHODS=openid` — no password fallback). No per-user roles to wire; Actual's whole model is one shared server login, not per-user RBAC.
- **Paperless-ngx**: native OIDC via django-allauth's `openid_connect` provider, configured through `PAPERLESS_SOCIALACCOUNT_PROVIDERS` (a JSON blob — see `apps/paperless/base/paperless-oidc-config.yaml`, an `ExternalSecret` templating the client secret into it) and `PAPERLESS_APPS=allauth.socialaccount.providers.openid_connect`. **platform-admins → Django superuser**: `PAPERLESS_SOCIAL_ACCOUNT_SYNC_GROUPS=true` + `PAPERLESS_SOCIAL_ACCOUNT_SYNC_SUPERUSER_GROUP=platform-admins`, matched against the same reusable `groups` claim (plain group name, `full_path = false`) already used for ArgoCD/Grafana's RBAC — re-evaluated on *every* login, unlike Immich v3.0.0's account-creation-only behavior, so removing someone from `platform-admins` correctly demotes them here too. Getting the group claim into the token at all needs Paperless's Keycloak client to request the `groups` optional scope (`keycloak_openid_client_optional_scopes.paperless`) *and* the provider's own `SCOPE` array in `PAPERLESS_SOCIALACCOUNT_PROVIDERS` to include `"groups"` — both sides have to ask for it. `PAPERLESS_DISABLE_REGULAR_LOGIN=true` blocks the frontend password form and rejects any password-based login attempt server-side, regardless of whether a local account exists (see the gotcha below on why one now does).
- **Vaultwarden**: `SSO_ENABLED=true`, `SSO_ONLY=true` (no local-password account creation — Keycloak is the only login path). SSO only gates *account* login: vault items are still encrypted client-side with a separate master password the IdP never sees, so this doesn't remove that step. `SIGNUPS_ALLOWED=true` is left on so a real Keycloak account's first SSO login can actually create a Vaultwarden account — worth tightening (e.g. an invite-only flow) once every real household account has logged in once; this was a judgment call, not something verified against a documented "correct" setting, so revisit it live. Vaultwarden's `/admin` panel is gated by a separate static `ADMIN_TOKEN`, unrelated to Keycloak.
- **Homebox**: `HBOX_OIDC_ENABLED=true`, `HBOX_OPTIONS_ALLOW_LOCAL_LOGIN=false`. No app-wide admin role to wire — Homebox's ownership model is per-household (the first user of a household becomes its owner), not a single superuser concept like Paperless's.
- **Vikunja**: `VIKUNJA_AUTH_OPENID_PROVIDERS_KEYCLOAK_*` env vars (a freely-chosen provider key, `keycloak`, that must match the `/auth/openid/<key>` redirect URI registered on its Keycloak client), plus `VIKUNJA_AUTH_LOCAL_ENABLED=false` and `VIKUNJA_SERVICE_ENABLEREGISTRATION=false` (no password fallback, no local self-registration). `AUTHURL` is Keycloak's realm base URL, not a literal authorization endpoint — Vikunja does its own OIDC discovery from that issuer, same pattern as Homebox's `HBOX_OIDC_ISSUER_URL`; confirmed live via Vikunja's own `/api/v1/info` endpoint reporting back a real, discovery-resolved `auth_url` (`.../protocol/openid-connect/auth`) rather than a static value. No per-user roles to wire — same reasoning as Homebox, no single app-wide admin concept.
- **Mealie** (#56): `OIDC_AUTH_ENABLED=true`, `OIDC_SIGNUP_ENABLED=true`, `ALLOW_PASSWORD_LOGIN=false`. Unlike Vikunja's issuer-URL-only `AUTHURL`, Mealie's `OIDC_CONFIGURATION_URL` wants the *full* discovery document URL — confirmed against its own docs, `.../realms/homelab/.well-known/openid-configuration`, not just the realm base. **platform-admins → Mealie admin**: `OIDC_ADMIN_GROUP=platform-admins`, matched against the same reusable `groups` claim as Paperless-ngx/ArgoCD/Grafana (`keycloak_openid_client_optional_scopes.mealie` requests the `groups` optional scope, same as Paperless's client) — plain group-name matching, no client-role wiring needed, same shape as Paperless's superuser sync. Mealie also has an `OIDC_USER_GROUP` variable, but it does something none of this repo's other group variables do: membership in it is *required* to log in at all, regardless of `OIDC_ADMIN_GROUP` membership — left unset here on purpose, since setting it would break this repo's established "any Keycloak-authorized identity gets in" access model that every other app on this page follows. Verified live past "the client exists": Mealie's own `/api/auth/oauth/native/config` endpoint reported a real, discovery-resolved `authorization_endpoint` (`.../protocol/openid-connect/auth`) with the correct `client_id` and a `scope` that included `groups`, confirming both the discovery chain and the optional-scope wiring worked end to end.
- **LubeLogger** (#55): `OpenIDConfig__AuthURL`/`__TokenURL` are literal Keycloak endpoint URLs (`.../protocol/openid-connect/auth` and `.../token`), not a discovery document — confirmed against the app's own `Models/OIDC/OpenIDConfig.cs`, LubeLogger builds its authorize redirect directly from these two fields with no OIDC-discovery step of its own, unlike every other app on this page. `OpenIDConfig__UsePKCE=true` per #55's own scope ("no reason not to"); `OpenIDConfig__Scope=openid email` matches the app's own coded default (its JWT parser reads the `email` claim straight off the id_token, falling back to a `UserInfoURL` call only if that claim is missing — not needed here since Keycloak includes it by default). No group/role wiring: LubeLogger has no group-claim support at all, confirmed against its source — same "no single app-wide admin concept" reasoning as Homebox/Vikunja. Verified live via `/Login/GetRemoteLoginLink`, an unauthenticated endpoint that returns the exact authorize URL the app would redirect a browser to: confirmed it resolves to Keycloak's real endpoint with the correct `client_id`/`redirect_uri`/`scope` and a real S256 PKCE challenge, and that fetching that URL renders Keycloak's actual "Sign in to Homelab" login form (not an "invalid redirect URI" error) — the same discovery/wiring-correctness bar as Mealie/Vikunja, short of an actual interactive browser login.

### A real gotcha found live: Paperless-ngx's open signup window on a fresh install

The first real visit to `paperless.dev.thepugh.family` — before anyone had ever logged in via Keycloak — landed on what looked like a "create a superuser" signup page instead of going straight to Keycloak. Root cause, confirmed against the actual source (`src/documents/context_processors.py`'s `FIRST_INSTALL`, `src/documents/allauth_adapter.py`'s `is_open_for_signup`): paperless-ngx computes `FIRST_INSTALL` as "zero real `User` rows and zero `Document` rows exist," and when that's true, the login page unconditionally redirects to `/accounts/signup/` (django-allauth's local account registration) via inline JavaScript — **completely independent of `PAPERLESS_DISABLE_REGULAR_LOGIN`**, which only hides the password form and rejects password-based login attempts, but has no effect on this specific redirect or on `is_open_for_signup()`. On a genuinely empty database, this meant *whoever visited the app first* — not necessarily the intended `platform-admins` member — could register a local account there and be auto-granted Django superuser.

The fix isn't a config toggle (none exists), it's removing the precondition: `PAPERLESS_ADMIN_USER`/`PAPERLESS_ADMIN_PASSWORD` (consumed by the `manage_superuser` management command paperless-ngx's own entrypoint runs at container start) creates one real `User` row before anyone can ever visit, permanently falsifying `FIRST_INSTALL` and closing the `/accounts/signup/` bypass for good. This bootstrap account (`bootstrap-admin`, password ksops-encrypted in `apps/paperless/base/paperless-config.enc.yaml` even though it's provably inert) coexists safely with the `platform-admins` → superuser group-sync above — confirmed against the source that group sync (`handle_social_account_updated`) only ever mutates the specific user tied to a social login, never touching unrelated local rows — and can never itself be used to log in, since `PAPERLESS_DISABLE_REGULAR_LOGIN` rejects password auth unconditionally regardless of which account is attempting it. Verified live: after creating the bootstrap account, the login page no longer contains the signup-redirect script and shows only the Keycloak button, and a direct POST attempt to log in as `bootstrap-admin` with its real password is rejected with "Regular login is disabled" — not just "the config looks right."

### Forward-auth: changedetection.io, Pinchflat

changedetection.io has no OIDC/SSO integration at all — confirmed against the project's own tracker (a feature request has been open since 2022 with no implementation), it only supports a single shared password. This is the first *real* app to use the `oauth2-proxy` + Ingress `auth-url`/`auth-signin` forward-auth template documented in the [Onboard a New App](../guides/onboard-a-new-app.md) guide and proven by the `sso-demo` reference deployment — copied as plain manifests under `apps/changedetection/base/` (`oauth2-proxy.yaml`) rather than the Tofu-managed Helm release `sso-demo` uses, matching every other app under `apps/` being plain Kustomize resources.

Two Ingresses share one hostname, same split as `sso-demo`/`whoami`: oauth2-proxy's own Ingress owns `/oauth2` and the actual TLS Certificate (`cert-manager.io/cluster-issuer` annotation); changedetection's Ingress handles `/` and reuses the same `secretName` without its own cluster-issuer annotation, avoiding two Certificates racing to manage one Secret. The same `proxy-buffer-size: "16k"` annotation `sso-demo` needed (oauth2-proxy's session cookie bundles Keycloak's access/ID/refresh tokens, routinely exceeding ingress-nginx's default buffer) is carried over here too, applied proactively rather than waiting to hit the same 502 live again.

**Pinchflat switched to this same pattern after initially shipping with its own static basic auth instead** (`BASIC_AUTH_USERNAME`/`BASIC_AUTH_PASSWORD`). That first pass wasn't a mistake in isolation — #54's own scope flagged a real, considered tradeoff: Pinchflat's podcast RSS-feed and video-stream routes need to stay reachable *without* authentication for podcast apps to consume them, and oauth2-proxy in front of the whole app would break that unless a path-based exception was carved out. Reading Pinchflat's own source (`lib/pinchflat_web/router.ex`, `lib/pinchflat_web/plugs.ex`) found that Pinchflat already ships exactly this exception itself, gated by its own `EXPOSE_FEED_ENDPOINTS` setting — and since that setting was already staying off (no off-LAN podcast consumption need per #54's own scope), the RSS concern never actually applied either way. Basic auth technically worked, but it broke a real pattern every other app on this page follows: a second, app-specific credential set to remember, unlike every other app here (native OIDC or this same forward-auth template). Once pointed out, switching to oauth2-proxy — copied from changedetection.io's own worked example above, same two-Ingress split and `proxy-buffer-size` annotation — removed that second credential set entirely, at no cost, since `EXPOSE_FEED_ENDPOINTS` staying off meant the RSS-exception concern was never actually in play for this deployment.

A real gotcha hit live during that switch: oauth2-proxy's `cookie_secret` must be a raw string of exactly 16, 24, or 32 *bytes* — not a base64-encoded value of that many decoded bytes. Generating it with `openssl rand -base64 32` (the natural instinct, and what most oauth2-proxy documentation examples show) produces a 44-character string that decodes to 32 bytes but *is* 44 bytes as a literal string, and oauth2-proxy checks the literal string length here, not the decoded length — it crash-looped immediately with `cookie_secret must be 16, 24, or 32 bytes to create an AES cipher, but is 44 bytes`. Fixed with `openssl rand -hex 16` instead (32 hex characters = exactly 32 raw bytes), matching the plain-random-string shape changedetection.io's own working cookie-secret already uses. Worth remembering for any future oauth2-proxy cookie-secret: generate a raw N-character string directly, don't base64-encode it first.

### A real gotcha researched, not hit live: LubeLogger ships with authentication off

Reading `appsettings.json` before deploying turned up something none of this repo's other apps do: `"EnableAuth": false` is LubeLogger's own shipped default, and its `Authen` middleware (`Middleware/Authen.cs`) implements this literally — when `EnableAuth` is false, *every* request is silently authenticated as a fake root/admin identity with no login screen at all, regardless of whether OIDC is configured. This is a deliberate upstream first-run UX choice, not a bug: the intended bootstrap flow is to visit the (open) app once, go to Settings, and enable authentication there, which is also where local root credentials get created.

That flow doesn't compose cleanly with OIDC-only login, though. `EnableAuth` genuinely is a supported env var (`configuration["EnableAuth"]` is read directly), so setting it `true` from the very first deploy is possible in principle — but LubeLogger matches OIDC identities against **pre-existing local user records by email** (confirmed against `Logic/LoginLogic.cs`'s `ValidateOpenIDUser`: no auto-provisioning on first login, unlike every other app on this page), and a fresh SQLite DB has zero such records. Flipping `EnableAuth=true` blind on day one, with no root user configured and no matching OIDC account yet, would lock everyone out with no way back in short of editing the database directly. (LubeLogger does have a narrow escape hatch for exactly this — `EnableRootUserOIDC=true` + `DefaultReminderEmail=<an email>` lets one specific address log in via OIDC with no local account required — but wiring a real person's email address into committed YAML would cut against this repo's standing "RBAC by Keycloak group, not hardcoded personal identity" practice, for a value that's a one-time bootstrap convenience, not ongoing access control.)

So `EnableAuth` is deliberately left unset in `apps/lubelogger/base/lubelogger.yaml` (upstream's own default), with a comment explaining why, and enabling it is left as a manual step for whoever actually deploys this: open the app once while it's still unauthenticated, go to Settings, and turn authentication on (optionally via the root-OIDC escape hatch above, using your own email, entered live rather than committed) — the same "managed by hand, not by Tofu" precedent already established for Keycloak group membership. This was resolved via reading `Authen.cs`/`LoginLogic.cs`/`appsettings.json` directly before ever deploying, the same research-before-deploying approach that avoided a live crash loop for Mealie's uid/entrypoint question — not something hit as a live failure here.

A smaller, related fix from the same research pass: ASP.NET Core's Data Protection key ring (used to encrypt LubeLogger's own login cookies) defaults to `$HOME/.aspnet/DataProtection-Keys`, which resolves to `/root` when the upstream image runs as root (confirmed against its own `docker-compose.yml`, which mounts exactly that path) but is unset entirely for an arbitrary non-root uid with no `/etc/passwd` entry — the same class of bug already fixed for Velero's kopia repo path via an explicit `HOME` env var. `HOME=/App/data` redirects the key ring onto the persistent PVC instead; confirmed live that `/App/data/.aspnet/DataProtection-Keys` is created there on first boot, so login sessions survive a pod restart rather than invalidating on every one.

## Homepage: no PVC, no Velero, its own auth gate

[gethomepage.dev](https://gethomepage.dev)'s service dashboard (#59), structurally unlike every app above: its entire config (`services.yaml`, `widgets.yaml`, `settings.yaml`, `bookmarks.yaml`) is plain YAML, so it lives in a `ConfigMap` mounted read-only rather than a PVC — this repo's only real app needing neither StorageClass. No PVC means no `backup.velero.io/backup-volumes` annotation either: there's nothing stateful to protect, since the config itself is already tracked in git.

**Static config, not Kubernetes auto-discovery.** Homepage can auto-discover services via `gethomepage.dev/*` annotations on `Ingress`/`Service` objects, but that needs a `ServiceAccount` with read access to the Kubernetes API — this repo's first app that would talk to the k8s API at all, since every other app here is fully self-contained. Went with hand-authored `services.yaml` instead, matching this repo's existing preference for explicit/reviewable config over auto-discovery (the same reasoning behind the DNS wildcard-record-over-ExternalDNS decision). Every app hostname in `services.yaml` uses Homepage's own `{{HOMEPAGE_VAR_*}}` config templating (one `HOMEPAGE_VAR_DOMAIN_SUFFIX` env var, wired from the usual per-environment token) rather than a Kustomize `replacements:` target per link — cleaner here since the same domain suffix appears many times in one YAML blob, which `replacements:`' delimiter/index model isn't built to do more than once per field.

**Native OIDC, v2.0+.** `HOMEPAGE_OIDC_ISSUER`/`_CLIENT_ID`/`_CLIENT_SECRET` (plus `HOMEPAGE_AUTH_ENABLED=true` and a `HOMEPAGE_AUTH_SECRET` signing secret — ksops-encrypted, no Tofu counterpart, same shape as Homebox's `api-key-pepper`). No oauth2-proxy needed. Per Homepage's own docs, though, it applies **no claim-based authorization of its own** — it grants access to any identity Keycloak authorizes for this client, same as this repo's other native-OIDC apps (a real Keycloak account is already this homelab's access gate; nothing analogous to Immich's/Paperless-ngx's `platform-admins` role mapping was needed).

Chose the RBAC-free static-config path deliberately over auto-discovery — the recommended default in #59's own scope — rather than revisiting it as a future improvement.

### Four real gotchas found live deploying Homepage

The first three surfaced as the container crashing well past readiness — a server-side probe failure, a 500 on the OIDC sign-in path, and a crash loop under real logged-in use — not a config-looks-wrong problem. The fourth is a standing operational gotcha, not a one-time bug: it recurs every time a new app is added to the dashboard.

1. **kubelet's own probes get rejected by Homepage's host-validation.** `HOMEPAGE_ALLOWED_HOSTS` (the Next.js host-header allowlist) only had the real Ingress hostname in it — but kubelet's readiness/liveness `httpGet` probes hit the pod's IP directly, not that hostname, and got a `400`/`Host validation failed for <pod-ip>:3000` in the logs. Fixed by including the pod's own IP:port via the downward API (`MY_POD_IP` fieldRef, `HOMEPAGE_ALLOWED_HOSTS=$(MY_POD_IP):3000,__APP_HOSTNAME__`) — exactly what gethomepage.dev's own Kubernetes install example does, and the reason it does it, which wasn't obvious until this broke live.
2. **The image auto-populates *every* skeleton config file it doesn't find, and can't write them as non-root.** Only the 4 files Homepage's own config actually needs (`services.yaml`, `widgets.yaml`, `settings.yaml`, `bookmarks.yaml`) were originally mounted; at startup the entrypoint also tries to copy the rest of its skeleton config from its own image into `/app/config` for any it doesn't find — and crashed with `EACCES` the moment a real request needed one, since `/app/config`'s directory isn't writable under `runAsNonRoot`. The same failure mode also broke logging: Homepage writes its own log file under `/app/config/logs`, and without a separate writable mount there, trying to log the *original* error crashed the request with a second, more confusing `EACCES` instead — a real OIDC auth attempt surfaced as an opaque 500 with no useful log line until this was fixed. Fixed by mounting every skeleton file (the 4 real ones plus every remaining one left empty) via `subPath` plus a dedicated `emptyDir` at `/app/config/logs`.
3. **gethomepage.dev's own Kubernetes example doc is missing one skeleton file, `proxmox.yaml`.** Mounting the 8 files that doc lists (matching gotcha 2 above) looked sufficient — the pod passed every health check and the OIDC sign-in flow verified clean — but only because nothing had lazily touched `proxmox.yaml` yet. The first real logged-in dashboard view crashed the container on exactly the same `EACCES` failure mode as gotcha 2, this time on a file the docs never mentioned, producing an "API Error" banner and every service entry showing "Error" (the pod was crash-looping under real request load, not failing each site check individually). Confirmed the *actual*, complete file list by shelling into a throwaway debug pod running the same image and listing `/app/src/skeleton/` directly, rather than trusting the docs a second time — 9 files, not 8. Worth remembering for any future Homepage version bump: re-check that list against the live image rather than assuming it's stayed fixed at 9.
4. **A new dashboard entry never appears on its own — not because of the static-config decision itself, but because of gotcha 2's own fix.** Every config file (`services.yaml` included) is mounted via `subPath`, which was necessary to work around gotcha 2 — but `subPath`-mounted ConfigMap volumes are a well-known Kubernetes limitation: unlike a whole-directory ConfigMap mount, they never get live-updated in a running pod, no matter how long you wait or how many times the ConfigMap itself changes. Confirmed live while adding Vikunja to `services.yaml` (#58): applying the updated `ConfigMap` alone left the already-running pod's mounted file unchanged, and even a full pod restart only picked up the new content because the restart itself re-establishes the `subPath` bind-mount from the ConfigMap's *current* contents at container-create time — the update was never streamed in. Since nothing in this Deployment ties the pod template to a hash of the ConfigMap's contents (the usual fix for this class of problem), **a config-only change needs a manual `kubectl rollout restart deployment/homepage -n homepage` after it syncs** — ArgoCD applying the new `ConfigMap` is not sufficient by itself. Worth automating (a checksum annotation via Kustomize) if this becomes a frequent enough chore; left as a manual step for now, consistent with this app's existing preference for explicit config over automation.

Verified live after the first three fixes: the pod stays healthy and its `resources` widget successfully collects real CPU/memory/filesystem stats under sustained real use, not just a passing health check — confirmation that the dashboard's cluster/app status entries display correctly instead of "Error" still needs an actual browser login.

## Pinchflat: internet egress, and a flagged backup gap

**Internet egress — a first for this repo.** Every other app on this page (and Mealie/changedetection.io specifically, despite both having features that could use it) deliberately has no route to the open internet — see Mealie's `network-policies.yaml` comment for why its own recipe-import-by-URL feature was left without it. Pinchflat's entire purpose is fetching content from YouTube via `yt-dlp`, so it's the first `apps/` namespace where that's genuinely in scope rather than an unused capability. `apps/youtube-archiver/base/network-policies.yaml`'s `allow-internet-egress` policy is scoped to the `app: pinchflat` pod label specifically (not namespace-wide) and to port 443 only — the same shape as Wikipedia's updater `CronJob` egress rule (#53), rather than extending `core-addons`' `allow-internet-egress` (`0.0.0.0/0`) pattern, currently reserved for 3 system namespaces, to an `apps/` namespace. Verified live: `kubectl exec` into the running pod reached `https://www.youtube.com` (`200`) and successfully ran the image's own bundled `yt-dlp` against a real public video, returning its actual title.

**The video library has no Velero coverage — a flagged decision, not an oversight.** `backup.velero.io/backup-volumes` is set only on `config` (the SQLite DB — subscriptions, download history), not `downloads` (the actual video files) — #54's own scope specifically asked for this to be an explicit, considered call rather than silently assumed covered the way Wikipedia's ZIM cache is. Unlike that cache (trivially re-fetchable from `download.kiwix.org`), archived YouTube videos are **not** reliably re-fetchable — source videos get deleted or made private over time — putting this closer to Immich's media library in "irreplaceable if lost" risk. It gets the same treatment Immich's media library already has: relying on the NAS's own offsite backup rather than Velero's File System Backup (which only covers Ceph-backed volumes here anyway — `downloads` is NFS-backed). Worth revisiting against the external-Kopia-repo idea discussed separately if this archive grows large enough that "re-download from the NAS's own backup" stops being a fast enough recovery path.

**A gotcha found live: GHCR's tags lag Pinchflat's GitHub Releases.** The newest GitHub Release at deploy time was `v2025.9.26`, but GHCR's own tag list (`ghcr.io/kieraneglin/pinchflat`) stops at `v2025.6.6` — confirmed by querying the registry's tags API directly rather than trusting the release page. `latest`'s image digest also doesn't match `v2025.6.6`'s, meaning the `:latest` tag tracks newer code than any versioned tag actually published to GHCR — the versioned-tag publish step appears to have lagged behind `latest` upstream at some point after `v2025.6.6`. Pinned to `v2025.6.6` here rather than `:latest` or a bare digest, consistent with this repo's pin-everything convention — worth re-checking GHCR's real tag list (not just GitHub's release page) on any future bump, doubly relevant given #54's own note that `yt-dlp` breaks periodically and needs ongoing image updates anyway.
