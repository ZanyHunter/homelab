ZanyHunter's Homelab

*arr Stack (Sonarr/Radarr/Prowlarr/qBittorrent)

An automated media-acquisition pipeline feeding into Jellyfin: Prowlarr manages indexers, Sonarr/Radarr watch for TV/movie releases and hand them to qBittorrent, and completed downloads get imported into the library Jellyfin already serves. The one hard requirement driving most of this app’s shape: qBittorrent’s torrent traffic exposes peer IPs to trackers/swarms in a way nothing else in this repo does, so it must go through a VPN tunnel — routed to a Switzerland exit, currently via Mullvad (switched from Proton VPN — see the Secrets section below for why).

Two apps, split by security posture, not by convenience

Everything here could have lived in one apps/arr-stack/ namespace. It doesn’t, because qBittorrent’s VPN sidecar (Gluetun) needs the NET_ADMIN Linux capability and /dev/net/tun to build its WireGuard tunnel and run its own kill switch — a capability this repo has never granted to any app before. NET_ADMIN is disallowed under both restricted and baseline Pod Security Standards, so it needs a privileged-PSA namespace, the same tier this repo otherwise reserves for exactly three infra DaemonSets (metallb-system, csi-driver-nfs, monitoring).

Rather than make the whole stack privileged, the split is:

  • apps/arr-stack/ — namespace arr-stack, restricted PSA. Sonarr, Radarr, Prowlarr, each with its own oauth2-proxy forward-auth instance. None of the three ever touches a peer or tracker directly — Prowlarr’s indexer queries and Sonarr/Radarr’s metadata-provider lookups are plain HTTPS, no different from any other app’s egress here.
  • apps/arr-downloader/ — namespace arr-downloader, privileged PSA (set directly as a namespace label, same GitOps mechanism every other app namespace uses — no Tofu change was needed; the three existing privileged namespaces are Tofu-managed for unrelated bootstrap-ordering reasons, not because setting a PSA label itself requires Tofu). One Deployment, two containers in the same pod: Gluetun and qBittorrent. This is the only way for qBittorrent’s traffic to actually transit Gluetun’s tunnel — Kubernetes’ network-namespace-sharing unit is the pod, and the classic Docker network_mode: service:gluetun pattern has no separate-Deployment equivalent here.

This was a real, user-confirmed tradeoff, not a default: an earlier draft considered putting the entire stack behind Gluetun to match “all traffic” literally, but that would have made the whole namespace privileged for no real security benefit (Sonarr/Radarr/Prowlarr never expose an IP to a stranger the way BitTorrent does) and would have meant Gluetun’s kill switch taking the entire stack offline if the tunnel ever drops, not just the downloader.

Sonarr/Radarr still need to reach qBittorrent’s API directly (to submit and monitor downloads) — this needs a cross-namespace NetworkPolicy pair (egress from arr-stack, ingress into arr-downloader), the second use of the precedent Matrix Authentication Service established for Synapse ↔ MAS (see Matrix’s MAS section) — the first NetworkPolicy shape in this repo naming another app’s namespace directly.

Storage: a third use of the static-PV-into-a-real-path pattern, first with per-environment paths

Jellyfin’s media library (Jellyfin) established mounting a static PV directly into a hand-populated NFS directory rather than a dynamically-provisioned PVC; Pinchflat extended it read-write for its own downloads. This is that pattern’s third use — and its first where the underlying path genuinely differs between dev and prod.

Jellyfin’s and Pinchflat’s shared paths were a deliberate exception to this repo’s usual per-environment split, justified because their content is either read-only or purely additive. This app is different: Sonarr/Radarr actively rename, hardlink, and delete files during import. A dev misconfiguration touching the real household library would have real consequences Pinchflat’s append-only downloads never risked — so storage here is scoped per environment instead, confirmed with the user rather than assumed:

  • dev: a new, isolated NFS directory (/mnt/Main/k8s-dev/arr-downloads/, created by hand, not under Jellyfin’s jellyfin-media export at all). Its contents are invisible to Jellyfin, which only ever reads the one real shared export — this exists purely to exercise the pipeline mechanics (Sonarr/Radarr/qBittorrent/OIDC/VPN egress) safely against disposable test content.
  • prod: a new Downloads/ subdirectory inside the real jellyfin-media export, alongside the existing Movies/TV Shows/Other/YouTube. Sonarr/Radarr organize real files directly into the same Movies/TV Shows folders Jellyfin already scans.

Every container mounts this tree at the identical absolute path — qBittorrent at /media/Downloads, Sonarr/Radarr at /media (giving them /media/Downloads, /media/Movies, /media/TV Shows) — specifically so Sonarr/Radarr can hardlink completed downloads into the library instead of copying them. Hardlinks require the source and destination to be on the same filesystem/mount; keeping every container’s view at the same path avoids needing Sonarr/Radarr’s separate “Remote Path Mapping” feature (the approach TRaSH-guides recommends).

Manual, one-time NAS prep is required before first deploy: create and chown/chmod (uid/gid 1000) the Downloads/Movies/TV Shows tree under both the dev-only path and (if not already shaped this way) prod’s jellyfin-media export.

Networking

Standard per-namespace trio (default-deny-all, allow-dns-egress, allow-same-namespace) in both namespaces, plus:

  • Internet egress for Sonarr/Radarr/Prowlarr: the exact rule shape Pinchflat established (apps/youtube-archiver/base/network-policies.yaml) — scoped to those three pods’ labels, 0.0.0.0/0 on 443/TCP only.
  • Egress for the qBittorrent+Gluetun pod: 0.0.0.0/0, no port restriction — unlike every other egress rule in this repo. Originally scoped to just 51820/UDP (WireGuard) + 443/TCP (Gluetun’s startup calls), the same “can’t know the destination in advance” reasoning as LiveKit’s STUN-detection rule (apps/matrix-livekit/). Found live to be wrong for a different reason than the tun0 question below: BitTorrent needs arbitrary destination ports — DHT, peer connections, and tracker announces all use ports the client doesn’t control — so a real download stalled at 0% (dht_nodes: 0 in qBittorrent’s own /api/v2/transfer/info) until this was widened to unrestricted.
  • Cross-namespace Sonarr/Radarr → qBittorrent: covered above.
  • Gluetun’s own firewall (separate from Kubernetes NetworkPolicy — its own internal iptables kill switch) needs FIREWALL_INPUT_PORTS=8080 so Ingress/Sonarr/Radarr traffic can reach qBittorrent’s WebUI through Gluetun’s default-deny-inbound posture.

An open question that turned out not to matter: does this cluster’s CNI enforce NetworkPolicy against Gluetun’s internal tun0 interface (where qBittorrent’s actual torrent traffic exits post-tunnel) the same way it does the pod’s CNI-attached eth0? Still formally unverified either way (the policy has stayed unrestricted throughout, so nothing has actually tested a narrower rule against tun0 traffic) — but moot in practice now that real downloads work end-to-end (see Verification below); Gluetun’s own internal kill switch is the real leak-prevention mechanism regardless.

A second, unrelated root cause behind the same symptom, found after switching to Mullvad: even with the network genuinely working (Mullvad allows P2P, the tunnel connects, raw UDP DHT queries succeed from inside the pod), qBittorrent still reported dht_nodes: 0 and zero peers. qBittorrent’s own log showed why — its listening/DHT sockets bound only to the pod’s normal eth0 IP and loopback, never to tun0, on every restart including a fully fresh one. Gluetun and qBittorrent both start when the pod starts with no ordering guarantee between them; qBittorrent (fast-starting) enumerates and binds to whatever interfaces exist at that moment, and doesn’t rebind once tun0 appears later. Fixed by making Gluetun a native sidecar container (initContainers with restartPolicy: Always, stable since Kubernetes 1.29) with a startupProbe on its own health endpoint — this genuinely blocks qBittorrent’s container creation until Gluetun’s tunnel is confirmed healthy, not just until Gluetun’s own container has started. Confirmed live: qBittorrent’s log now shows it listening on 10.67.255.146 (the tunnel’s own IP) alongside the pod’s normal interfaces, dht_nodes populated to 161, and two real torrents began downloading at multi-MB/s with real peer counts.

Routing Sonarr/Radarr/Prowlarr’s own outbound traffic through the VPN too

The original design deliberately kept arr-stack’s three apps outside the privileged namespace and let them reach the internet directly (see Networking above) — reasonable for plain metadata-provider lookups, but the user later asked for indexer/tracker traffic specifically to route through the VPN as well, the same privacy reasoning that drove qBittorrent’s own tunnel in the first place, while keeping management traffic (Sonarr/Radarr/Prowlarr’s own APIs, qBittorrent’s download-client connection, Keycloak) local.

Gluetun ships a built-in HTTP proxy (HTTPPROXY=on, HTTPPROXY_LISTENING_ADDRESS=:8888) specifically for this: other containers can route arbitrary outbound traffic through its tunnel without sharing its pod’s network namespace, unlike qBittorrent’s own arrangement. FIREWALL_INPUT_PORTS gained 8888 alongside qBittorrent’s 8080, and a new gluetun-proxy Service exposes it. The cross-namespace NetworkPolicy pair gained a second rule (allow-arr-downloader-proxy-egress in arr-stack, matching ingress in arr-downloader) scoped to Sonarr/Radarr/Prowlarr (and any future app that needs it) on 8888/TCP — separate from the existing 8080/TCP qBittorrent-API rule, since Prowlarr needs the former but never the latter.

Each app’s own Settings > General > Proxy (API: PUT /api/v3/config/host for Sonarr/Radarr, /api/v1/config/host for Prowlarr) points at gluetun-proxy.arr-downloader.svc.cluster.local:8888. This has no per-purpose granularity — there’s no way to route “indexer traffic” specifically without also routing metadata-provider lookups (TheTVDB/TMDB/Fanart) through the same tunnel, since the proxy setting is all-or-nothing past whatever the bypass list excludes. Stated plainly rather than narrowed quietly: this is an accepted, low-cost side effect (arguably a privacy improvement), not a gap.

A real gotcha found live: proxyBypassLocalAddresses: true (the built-in “skip the proxy for local addresses” toggle, already the default) does not cover Kubernetes’ own cluster-DNS hostnames (qbittorrent.arr-downloader.svc.cluster.local) — enabling the proxy with only that toggle broke Sonarr’s own qBittorrent connectivity outright (DownloadClientCheck failed: “Unable to communicate with qBittorrent”), confirmed live via a forced health check, not assumed. Fixed with an explicit proxyBypassFilter (*.arr-stack.svc.cluster.local,*.arr-downloader.svc.cluster.local,*.cluster.local) on all three apps — after which internal traffic (qBittorrent’s API, Prowlarr’s own Application-sync calls to Sonarr/Radarr) stays direct while everything else routes through Gluetun’s tunnel.

qBittorrent tags from Sonarr/Radarr: not actually possible

Web research ahead of this work claimed Sonarr/Radarr’s qBittorrent download-client integration could tag each torrent with its source indexer’s name. Found live to be wrong, on two counts: the actual GET /api/v3/downloadclient/schema response for the QBittorrent implementation has no tag-related field at all (only tvCategory/movieCategory, already configured — see the guide), and Radarr#7588, the GitHub issue that research surfaced, turns out to be a feature request explicitly closed Won’t Fix by the Radarr maintainers, not a description of shipped behavior. There is no built-in way to do this from Sonarr/Radarr’s side. The existing per-app qBittorrent Categories (tv-sonarr, radarr) remain the practical way to distinguish arr-managed downloads by source at a glance; a genuine per-indexer tag would need a third-party companion tool (e.g. qBitrr2), not attempted here.

Images: hotio, and a real gotcha that changed arr-stack’s PSA level

Sonarr, Radarr, Prowlarr, and qBittorrent all use ghcr.io/hotio/*:release rather than the more commonly-referenced lscr.io/linuxserver/* images, chosen expecting hotio to run as an arbitrary non-root uid directly rather than needing linuxserver.io’s root-start-then-drop model. Found live to be wrong: hotio’s images use the identical s6-overlay preinit as linuxserver.io’s. Forcing restricted PSA’s non-root-from-the-first-process onto them failed outright —

/package/admin/s6-overlay/libexec/preinit: fatal: /run belongs to uid 0 instead of 1000, has insecure and/or unworkable permissions, and we're lacking the privileges to fix it.

— for Sonarr/Radarr/Prowlarr, and a related failure crash-looped qBittorrent even without runAsNonRoot forced, because its container still had capabilities: {drop: ["ALL"]}, which strips CAP_CHOWN from root too: chown: changing ownership of '/config': Operation not permitted.

The real fix: apps/arr-stack/base/namespace.yaml moved from restricted to baseline PSA — the same can’t-quite-reach-restricted tier minio/velero already use for their own Helm hook Jobs (NetworkPolicies and Pod Security Admission) — and all four containers (Sonarr, Radarr, Prowlarr, qBittorrent) had runAsNonRoot/runAsUser/capabilities: drop: ["ALL"] removed from their securityContext entirely, letting s6-overlay’s preinit run as root and do its own chown/setup before dropping to PUID/PGID internally, exactly like a normal Docker deployment of these images would. apps/arr-downloader/ needed no namespace change (already privileged, a superset of baseline) — just the same container-level fix on qBittorrent’s own securityContext. allowPrivilegeEscalation: false stayed on all four; dropping privileges via setuid() doesn’t need privilege escalation, only gaining them would.

hotio doesn’t publish immutable per-version tags the way this repo otherwise prefers (only floating release/testing/nightly channels) — :release is the closest available, their own documented stable channel.

qBittorrent’s own login, on top of oauth2-proxy’s

Found live: completing Keycloak login through oauth2-proxy still landed on qBittorrent’s own separate WebUI login page. This is expected, not a bug in the forward-auth wiring — oauth2-proxy’s auth-url check happens entirely at ingress-nginx, gating whether a request reaches qBittorrent’s Ingress at all; it has no mechanism to also authenticate into qBittorrent’s own independent account system once the request is let through.

qBittorrent has a documented mechanism for exactly this “behind a reverse proxy with its own auth” scenario, applied here via its own WebUI API (POST /api/v2/app/setPreferences, matching this repo’s “managed by hand, not by Tofu/GitOps” precedent for admin-UI-only settings — done via the API instead of clicking through the UI, functionally identical):

  • web_ui_reverse_proxy_enabled: true + web_ui_reverse_proxies_list: "10.244.0.0/16" (the cluster’s pod CIDR) — without this, qBittorrent sees every request as originating from ingress-nginx’s own pod IP rather than the real client, since it doesn’t trust X-Forwarded-For from an untrusted source by default.
  • bypass_auth_subnet_whitelist_enabled: true + bypass_auth_subnet_whitelist — skips qBittorrent’s own login for trusted source IPs, since oauth2-proxy has already verified the user via Keycloak. This doesn’t widen access beyond what NetworkPolicy already permits — only ingress-nginx and Sonarr/Radarr can reach qBittorrent’s port at all.

Corrected after a real live test failed: the initial value (dev’s network_cidr, 192.168.160.32/27 — the real LAN/VPN subnet browser clients actually connect from) never matched. Checking ingress-nginx’s own access log for the failed request showed its $remote_addr was already 10.244.6.1 — a pod-network address, not the real client’s LAN IP — meaning something upstream of ingress-nginx (most likely kube-proxy/MetalLB’s default SNAT behavior for externalTrafficPolicy: Cluster) masks the real source IP before ingress-nginx ever sees it, so that’s also what it forwards via X-Forwarded-For. The actual working value is both CIDRs together: "192.168.160.32/27,10.244.0.0/16" — the pod CIDR covers what’s actually observed in practice, the LAN CIDR is kept in case a future path ever does deliver the real client IP unmasked.

Also set a permanent WebUI password in the same call — qBittorrent generates a new temporary one on every restart until an operator sets a real one, which would otherwise also silently break Sonarr/Radarr’s own download-client login to qBittorrent’s API on the next pod restart.

This lives entirely in qBittorrent’s own persistent /config state (its Ceph-backed PVC), not in git — same category as Jellyfin’s SSO plugin config or LubeLogger’s EnableAuth flag. A future qBittorrent PVC loss/recreation needs this redone by hand. See Wire Up the *arr Stack for the exact, reproducible commands — for this and every other piece of cross-app wiring below.

Recovering access when the permanent password itself is lost (found live, not anticipated): qBittorrent’s WebUI password isn’t recorded anywhere outside qBittorrent’s own config — losing it means editing WebUI\Password_PBKDF2 out of qBittorrent.conf directly. The naive approach (edit the file on the live PVC, then delete the pod) doesn’t work: the still-running qBittorrent process holds its own in-memory copy of the config and rewrites the file with the old password intact during its graceful-shutdown save, clobbering the edit before the new pod ever starts. The fix is to kubectl scale deployment gluetun-qbittorrent --replicas=0 first (fully stopping the process with nothing left to write the file back), edit the config via a temporary debug pod mounting the same qbittorrent-config PVC (RWO, so it can’t be mounted into two pods simultaneously — this is why the real qBittorrent pod has to be fully scaled down first, not just deleted), then scale back to 1 — on that clean boot, with no password hash present, qBittorrent generates and logs a fresh temporary password exactly like a first-ever deploy.

The rest of the pipeline: also runtime state, not git

Connecting the four apps to each other — qBittorrent as Sonarr/Radarr’s download client, real indexers in Prowlarr, Prowlarr synced out to Sonarr/Radarr — is the same category of thing as the login fix above: each app’s own persistent state, configured via its own API (equivalent to clicking through its own UI), not a Kustomize/Tofu-managed setting. Wire Up the *arr Stack has the full reproducible runbook; the short version:

  • Sonarr/Radarr’s own “default save path” for qBittorrent isn’t automatic just because the PVC is mounted at /media/Downloads — found live via Radarr’s health check reporting a RemotePathMappingCheck error against qBittorrent’s factory-default /app/qBittorrent/downloads, which doesn’t exist in this deployment.
  • Public indexers are genuinely hit-or-miss for live Cloudflare protection, independent of whether Prowlarr’s own definition flags FlareSolverr as needed — LimeTorrents, The Pirate Bay, and Magnet Cat all rejected live with "blocked by CloudFlare Protection" despite passing schema validation; Knaben, TorrentDownload, World-torrent, and YTS didn’t. Byparr (see below) fixed this for the first two live — Magnet Cat hits its own site-level rate limit (429) independent of Cloudflare, not chased further.
  • Adding an indexer to Prowlarr alone does nothing for Sonarr/Radarr — Prowlarr’s own “Applications” connection (POST /api/v1/applications) is the actual sync mechanism, confirmed live by a real search query returning 185 results with real seeder counts across the configured indexers.
  • Auto-rename on import (PUT /api/v3/config/naming, renameEpisodes/renameMovies: true) and qBittorrent’s own seeding-ratio target (POST /api/v2/app/setPreferences, max_ratio: 1.5 with max_ratio_act: 0 — confirmed against qBittorrent’s own WebUI API docs to mean “pause,” not “remove,” at target) are both single-call runtime settings, same category as everything else in this section.

Byparr, Bazarr, and Tdarr: three more apps joining arr-stack

All three join the existing arr-stack namespace directly (no new namespace, no new PSA consideration) rather than each getting their own — none of them needs Gluetun’s NET_ADMIN, and Bazarr/Tdarr are tightly coupled to the same media library Sonarr/Radarr already mount.

Byparr (ghcr.io/thephaseless/byparr) is a Cloudflare-bypass proxy for Prowlarr’s indexers — an actively-maintained, API-compatible drop-in for FlareSolverr (chosen over the literal FlareSolverr project specifically because its own development has slowed relative to Byparr’s). Wired into Prowlarr as an indexer proxy (POST /api/v1/indexerproxy, implementation: FlareSolverr — Byparr deliberately implements FlareSolverr’s exact API, so Prowlarr never needs to know the difference), tagged (flaresolverr tag, shared between the proxy and the specific indexers that need it) rather than applied namespace-wide, so indexers that don’t need Cloudflare-bypassing aren’t slowed down by routing through a full browser unnecessarily. Deliberately has no Ingress/oauth2-proxy/Keycloak client of its own — it’s a pure internal service other arr-stack apps call, with nothing worth a human browsing to directly, unlike every other app in this stack.

Found live: the default 1Gi memory limit OOMKilled Byparr on its very first real page navigation — Camoufox (the hardened Firefox build Byparr uses instead of a lightweight headless shim) needs real headroom, not the couple hundred MB a simple scraping tool might. Fixed with a 1Gi request / 2Gi limit. Confirmed working past “the pod is Running”: a real request.get against a public URL succeeded end-to-end (browser launch, page navigation, response returned), and — the actual point of deploying it — LimeTorrents and The Pirate Bay, both previously rejected live with "blocked by CloudFlare Protection" (see above), now return real search results (40 and 100, respectively) through Byparr.

Byparr’s own outbound traffic is pointed at the same Gluetun HTTP proxy as Sonarr/Radarr/Prowlarr (HTTP_PROXY/HTTPS_PROXY env vars, with a NO_PROXY list mirroring the others’ proxyBypassFilter) — it’s genuinely “indexer traffic” by this app’s own scoping (fetching Cloudflare-protected tracker pages), so it rides the VPN tunnel the same way.

Bazarr (lscr.io/linuxserver/bazarr) is a subtitle manager — watches Sonarr’s and Radarr’s libraries and downloads matching subtitles. LinuxServer.io’s image (no hotio equivalent exists), same s6-overlay root-start model as every other app here, already accommodated by baseline PSA. Mounts the same arr-media-rw PVC Sonarr/Radarr/qBittorrent already share — no new PV/PVC, just another consumer of the existing claim. Gated by the standard oauth2-proxy template (new Keycloak client bazarr-oauth2-proxy).

Bazarr’s settings API takes a genuinely different shape than Sonarr/Radarr/Prowlarr’s clean JSON REST APIs: POST /api/system/settings expects form-encoded, dot-path keys (settings-sonarr-ip=..., settings-general-use_sonarr=true), not a JSON body matching the GET response’s nested shape (posting the latter returns 204 but silently changes nothing — found live, not assumed). Enabling a language (languages-enabled=en, a multi-value form field) and creating a language profile (languages-profiles=<JSON array>, one of the few fields that is JSON, just wrapped in a form field) both use this same style. Verified live past “the settings saved”: Bazarr’s own SignalR clients connected to both Sonarr and Radarr and pulled real library data (1 series found in dev’s test library) with no connection errors in its logs. English-only, per the user’s choice — subtitle provider signup (OpenSubtitles.com or similar) is left as a manual follow-up needing the user’s own account credentials, same class as every other externally-sourced credential in this repo; embedded-subtitle extraction (use_embedded_subs, already on by default) needs no provider account at all and works today.

Tdarr (ghcr.io/haveagitgat/tdarr) is a library health-check/transcode tool — combined server+node in one pod (internalNode: true), software (CPU) transcoding only for this pass per the user’s explicit choice (no /dev/dri passthrough, no Talos iGPU system extension). Also mounts arr-media-rw, plus a separate NFS-backed tdarr-cache PVC (100Gi, dynamically provisioned on nfs-dev/nfs-prod — not another static-PV-into-a-real-path instance, since it’s just scratch space with no pre-existing directory to point at) for in-progress transcodes, since emptyDir would be backed by the node’s 20GB root disk, far too small next to a 50GB+ UHD source file mid-transcode.

Found live: Tdarr ships 257 community plugins bundled directly in the image — no internet access needed for the base plugin set. Its plugin/flow marketplace (searching for additional/updated plugins) is a separate thing that does need real internet egress, confirmed live when search-flow-templates returned an empty result set with no egress rule present — this app was deliberately left with no internet-egress rule in the original design (“unless a future plugin/flow setup genuinely needs it”), and this is exactly that case, so it was added. The actual transcode logic uses Tdarr’s classic plugin-stack mechanism (a plain pluginIDs array on the Library object, applied via cruddb’s update mode) rather than the newer node-graph Flow editor — deliberately: constructing a Flow’s React-Flow-style graph (node positions, edge handles) blind via API carries real risk of a silently-broken pipeline that Tdarr’s own visual editor is specifically built to validate interactively, while the classic mechanism is a plain array Tdarr’s server-side code already validates. The one bundled plugin already matches this app’s exact starter-config goal: Tdarr_Plugin_vdka_Tiered_CPU_CRF_Based_Configurable skips any file already HEVC, re-encodes everything else to HEVC/x265 (CPU, libx265) at a per-resolution CRF (SD 20 / HD 22 / FullHD 24 / UHD 28 — lower value regenerates a bigger, worse-preserved file; these are the plugin’s own sensible defaults), and — the part that matters most for “keep UHD and Atmos, but compress the big files” — stream-copies audio and subtitles untouched (-c:a copy -c:s copy), so Atmos/TrueHD/DTS:X survive completely intact regardless of resolution tier.

One low-stakes rough edge, not chased further: an accidental duplicate Library entry (from a retried API call before the exact cruddb mode names were confirmed) couldn’t be deleted via any cruddb mode this session found (removeByDB returns 200 but doesn’t remove the row) — disabled instead (process_library: false, confirmed harmless: Tdarr only scans libraries with this flag true) rather than left fully cleaned up. Removing it properly is a one-click action in Tdarr’s own Library management UI, left as a trivial manual follow-up.

Seerr: a request manager, in its own namespace

Seerr (ghcr.io/seerr-team/seerr) is a request-management frontend connecting to Jellyfin and Sonarr/Radarr — the maintained successor to Jellyseerr and Overseerr, which merged into one codebase (Jellyseerr itself is now deprecated; the image reference and every setting below is Seerr’s own, not carried over from either predecessor).

Unlike Byparr/Bazarr/Tdarr, Seerr got its own namespace (apps/media-requests/, restricted PSA) rather than joining arr-stack — it isn’t security-coupled to the VPN/hotio posture the other three share, and its image runs as a plain non-root user with no root-start dance (confirmed live: both pods reached Running/Ready on the very first apply, no PSA gotcha the way every hotio/LinuxServer.io image in this stack hit). Gated by the standard oauth2-proxy template (new Keycloak client seerr-oauth2-proxy) — Seerr’s own OIDC support is preview/experimental only (inherited from the Jellyseerr codebase), so this is the stable option, consistent with every other non-native-OIDC app here.

Two new cross-namespace NetworkPolicy rules (a further use of the MAS↔Synapse precedent, now used a third time in this repo): media-requests → arr-stack (Sonarr 8989, Radarr 7878) and media-requests → jellyfin (8096). Confirmed live, not just present: from inside Seerr’s own pod, real requests to sonarr.arr-stack.svc.cluster.local:8989/ping, radarr.arr-stack.svc.cluster.local:7878/ping, and jellyfin.jellyfin.svc.cluster.local:8096/health all got genuine application-level responses, not timeouts.

The remaining setup is a real manual step, not yet completed: Seerr’s very first action is its own setup wizard, which requires signing in with a real Jellyfin account (POST /api/v1/auth/jellyfin) before any other settings endpoint accepts requests — confirmed live, POST /api/v1/settings/jellyfin returns 401 cookie 'connect.sid' required without first completing that sign-in. This genuinely needs the user’s own Jellyfin credentials (or a fresh account created for the purpose), same “managed by hand” category as Jellyfin’s own SSO plugin config — not something to work around with a guessed or synthetic credential. Left as the actual next step:

  1. Log into Seerr’s setup wizard with a real Jellyfin account (this becomes Seerr’s admin, with full “Manage Requests” permission automatically).
  2. Connect Sonarr and Radarr (API keys, quality profile, root folder) so requests actually submit downloads.
  3. Do not grant “Manage Requests”/auto-approve to any other imported account afterward — Seerr’s own default (requests need approval unless explicitly granted otherwise) is what satisfies “only I can approve requests”; the requirement is enforced by simply leaving every other account at its default permission level.
  4. No separate “trigger a Jellyfin reindex” integration to build — Seerr natively triggers a library scan once a request it submitted finishes importing via Sonarr/Radarr, inherent to how it already connects to Jellyfin in step 1.

Secrets

Four new Keycloak clients (sonarr-oauth2-proxy, radarr-oauth2-proxy, prowlarr-oauth2-proxy, qbittorrent-oauth2-proxy), one per app, following the same 1-app-1-client shape every other oauth2-proxy app here uses — deliberately not one client shared across all four oauth2-proxy instances, which would have been a genuinely new, unprecedented pattern in this repo. Each app’s own oauth2-proxy cookie secret is ksops-encrypted, generated via openssl rand -hex 16 (a raw 32-byte value — openssl rand -base64 32 produces a 44-character string that crashes oauth2-proxy, the exact bug already hit and fixed for Pinchflat).

Switched from Proton to Mullvad after finding live that Proton’s free plan blocks P2P/torrent traffic outright (confirmed directly against Proton’s own docs, https://protonvpn.com/torrenting: “you’ll need a paid plan to use our dedicated P2P servers for VPN torrent downloads and uploads”) — a hard provider-level ceiling no config change here could fix, surfaced as a real download stalling at 0% (dht_nodes: 0, zero peers on any tracker) even after the tunnel itself connected fine and genuinely egressed through Switzerland. Mullvad allows P2P on every server, no special subset to find, and has no free tier at all — a real paid subscription.

The WireGuard credentials (WIREGUARD_PRIVATE_KEY, WIREGUARD_ADDRESSES) have no Tofu counterpart — neither provider originates from this repo’s own generated state — so they stay ksops-encrypted in apps/arr-downloader/base/vpn-credentials.enc.yaml (renamed from proton-vpn-credentials.enc.yaml), same category as any oauth2-proxy cookie secret. Mullvad’s registration flow is the opposite of Proton’s: Proton’s account portal generates a full config including the private key server-side; Mullvad instead expects a locally-generated keypair, with only the public key ever uploaded (My devices → Advanced → Create device on their account portal) — confirmed live via a real screenshot after web research initially and wrongly concluded Mullvad had no such bring-your-own-key flow (both Gluetun’s own wiki and a fetched Mullvad help article described only the older mullvad-wg.sh-script/portal-config-download flow; the account portal’s newer self-service key-upload option isn’t reflected in either). The private key was generated locally with Python’s cryptography library (X25519, raw-encoded to match WireGuard’s format) since neither wg genkey nor sudo apt install wireguard-tools were available in-session — it never left this machine. wireguard-addresses is the IPv4 Mullvad assigns to the device on creation.

Resolved at prod-promotion time, before it became a real incident: vpn-credentials.enc.yaml originally lived in apps/arr-downloader/base/ — shared between dev and prod, meaning the promotion pipeline’s own development → main merge would have pushed dev’s live, actively-tunneling WireGuard credentials straight into prod’s Gluetun, both pods fighting over one Mullvad device identity. Caught before merging, not after: fixed by moving the secret out of base/ entirely into each environment’s own overlays/<env>/vpn-credentials.enc.yaml with its own ksops-generator.yaml and generators: entry — the first ksops-encrypted secret in this repo that has to be per-environment rather than shared, since a WireGuard private key is a real device identity to the VPN provider in a way an oauth2-proxy cookie secret never is. Prod got a second, genuinely separate Mullvad device (“quiet zebra”), registered the same locally-generated-keypair way as dev’s. Verified via the repo-server test-build pattern that dev’s and prod’s builds now render distinct wireguard-private-key/wireguard-addresses values, and confirmed applying the restructured dev manifests live caused zero pod restart (byte-identical secret content, just relocated) — dev’s already-running tunnel was undisturbed.

Verification

Verified live on dev, past the design-complete/test-build-only stage: keycloak-realm’s tofu apply created all four new oauth2-proxy clients cleanly (12 resources — client + random_password + kubernetes_secret each — zero drift elsewhere), both dev Kustomize builds were confirmed via the ArgoCD repo-server test-build pattern (ksops decrypting real secrets correctly, no leftover __TOKEN__ placeholders), and applying that output directly to dev showed:

  • The VPN actually works, not just “the pod is Running”: Gluetun’s own logs report a successful WireGuard handshake to Proton’s CH-FREE#11 endpoint, and its [ip getter] log line confirms the tunnel’s egress IP resolves to Switzerland, Zurich — the whole reason this app’s architecture looks the way it does, genuinely confirmed rather than assumed. Stable for 8+ hours with zero restarts on the Gluetun+qBittorrent pod.
  • The privileged-PSA/NET_ADMIN design is sound: the API server admitted the Gluetun+qBittorrent pod’s capability request under privileged PSA with no admission errors, on the first apply.
  • A real, live-found gotcha changed arr-stack’s PSA level from restricted to baseline — see the Images section above for the full story (hotio’s images need to start as root, same as linuxserver.io’s, which restricted flatly disallows).
  • All four apps reach a real Keycloak login, not just “the client exists”: an unauthenticated request to each hostname redirects through /oauth2/start to a real Keycloak authorize URL with the correct client_id/redirect_uri/scope for that specific app, and fetching Sonarr’s authorize URL rendered Keycloak’s actual Sign in to Homelab login form.
  • The new cross-namespace NetworkPolicy actually works: kubectl exec’d from Sonarr’s pod (arr-stack) to qBittorrent’s Service DNS (arr-downloader) and got a real HTTP response (403 Forbidden — qBittorrent’s own CSRF/auth check, not a network-level block; a blocked connection would have timed out with no response at all, not returned a real HTTP status).
  • Real Let’s Encrypt certificates issued for all four hostnames on the first apply.
  • A real post-merge gotcha, found by the user actually logging in: completing Keycloak login still landed on qBittorrent’s own separate login page (see the section above) — fixed via qBittorrent’s own API, confirmed by a fresh login with the new permanent password returning a real authenticated session (/api/v2/app/version succeeding, not a 403), and confirmed again by the user themselves after the fix landed on qBittorrent’s real interface with no second login prompt.
  • The full pipeline is wired and verified with real results, not just configured: qBittorrent added as Sonarr’s and Radarr’s download client (each confirmed via a forced health check showing no connectivity/path-mapping errors, not just “the object saved”); five public indexers added to Prowlarr; Prowlarr’s Application sync connected to both Sonarr and Radarr (each connection live-tested by Prowlarr before saving); and a real search query returning 185 results with real seeder counts across the configured indexers. See Wire Up the *arr Stack for the full reproducible runbook, including two real gotchas found along the way (qBittorrent’s own save-path setting, and public indexers that pass Prowlarr’s schema check but are live-blocked by Cloudflare anyway).

A real download, actually completing — not just configured, not just “the tunnel connects”: the user launched two real downloads (one from Radarr, one from Sonarr) through the UI. Both initially stalled at 0% with dht_nodes: 0 and zero peers, on Proton’s free plan — root-caused to Proton blocking P2P traffic outright at the provider level (see the Secrets section above), not a bug in this repo’s own config, confirmed by widening the egress NetworkPolicy to unrestricted first (a real, independently-needed fix, kept) and the stall persisting unchanged regardless. Switching to Mullvad fixed the provider-level block, but the exact same symptom (dht_nodes: 0) persisted even then — a second, unrelated root cause (Gluetun/qBittorrent container startup ordering, see Networking above), fixed with a native-sidecar restructure. After both fixes: connection_status: "connected", dht_nodes: 161, and both torrents genuinely downloading — one at ~1 MB/s, the other (a 57.7GB UHD release with 17 real seeders) at ~12 MB/s. This is the actual bar for “the *arr stack works,” not any of the individual pieces verified earlier.

Not yet exercised: the hardlink-into-/media/Movies-or-/media/TV-Shows import step once a download completes — the downloads were still in progress as of this writing, not finished. Also still unverified either way, and now unlikely to get a clean answer from this app alone: whether Kubernetes NetworkPolicy meaningfully constrains tun0 traffic specifically, since the policy has stayed unrestricted throughout real-download verification.

Round 2 (routing Sonarr/Radarr/Prowlarr’s own traffic through the VPN, plus smaller runtime settings), also verified live, not just applied: both dev Kustomize builds (the new gluetun-proxy Service, HTTPPROXY env vars, and the second cross-namespace NetworkPolicy rule) confirmed via the repo-server test-build pattern with no leftover tokens, then applied directly. Gluetun’s HTTP proxy confirmed genuinely tunneling traffic, not just listening: kubectl exec‘d from Sonarr’s own pod, a direct request to ipinfo.io returned the real homelab IP, while the identical request routed through gluetun-proxy.arr-downloader.svc.cluster.local:8888 returned Mullvad’s Swiss exit IP — a real before/after comparison, not just “the proxy accepted a connection.” After finding and fixing the proxyBypassLocalAddresses gotcha (see above), all three apps’ /api/v3/health (Prowlarr: /api/v1/health) came back clean except one pre-existing, unrelated finding (the “Torrent Downloads” indexer sync quirk noted above); a real Prowlarr search returned 134 live results through the now-proxied path, and Sonarr’s RSS sync completed successfully post-fix.

Public exposure and prod deployment both stay deferred, matching every other app in this repo’s rollout history.
