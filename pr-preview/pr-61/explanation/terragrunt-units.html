Terragrunt Units and Multi-Environment Layout

tofu/ used to be one flat root module — one state file, one environment (“dev”), no way to stand up a second cluster without clobbering the first. It’s now seven independently-applied Terragrunt units, each its own Tofu root module, wired together by dependency blocks that read a prior unit’s already-applied outputs. See Repository Layout for the exact directory tree.

Dependency graph: network → talos-cluster → core-addons → {backup, keycloak-infra, observability} → keycloak-realm.

Why units, not one module

Two concrete problems this solves:

  1. The Keycloak two-phase bootstrap. The keycloak provider authenticates with an admin password generated in the same apply — a value that’s unknown on a from-empty-state plan, which the old flat module couldn’t resolve without a manual tofu apply -target=time_sleep.wait_for_keycloak first. Splitting keycloak-infra (creates the password) from keycloak-realm (uses it) into separate units fixes this structurally: keycloak-realm’s dependency block on keycloak-infra sets mock_outputs_allowed_terraform_commands = ["init", "validate", "plan"] — not "apply" — so terragrunt run --all apply refuses to synthesize a fake password at apply time. It blocks until keycloak-infra has genuinely finished applying and produced a real, known password, then generates the keycloak provider block with that literal value. No targeting, no bootstrap incantation to remember.
  2. Real dev/prod separation. Each environment under tofu/live/ is just another directory of the same seven units, with its own env.hcl and its own generated state paths (see Remote Tofu State) — nothing shared, nothing to clobber.

How units talk to each other

  • State: each unit gets its own file, generated by tofu/live/root.hcl’s remote_state block — see Remote Tofu State.
  • Providers: each unit’s terragrunt.hcl has a generate "provider" block. Units needing cluster access (everything past talos-cluster) build their kubernetes/helm provider config from dependency.talos_cluster.outputs.kubernetes_client_configuration — the same attributes a single providers.tf used to read directly off talos_cluster_kubeconfig.this before the split. keycloak-realm additionally builds a keycloak provider from dependency.keycloak_infra.outputs.admin_password.
  • Secrets: tofu/secrets.enc.yaml (unchanged location/mechanism) is decrypted via a generate "secrets" block, but only into the units that actually need Proxmox/Unifi/Cloudflare credentials — network, talos-cluster, and core-addons. backup, keycloak-infra, observability, and keycloak-realm never get it, so their state can never contain those credentials.
  • A real dependency, not just ordering: talos-cluster reads its VLAN ID from dependency.network.outputs.vlan_id rather than a separately-supplied variable — the old flat module had a # depends_on = [unifi_network.this] that was commented out and never enforced anything. Now there’s one source of truth.

For the exact commands to run everything, or to bring up a new environment, see the Deploy From Scratch and Stand Up a New Environment guides.

Cautions learned from testing this live

Terragrunt’s dependency blocks make a from-scratch run --all apply genuinely one command — verified with a real destroy-then-recreate of the entire dev environment, not just a read of the docs. Three real bugs were found and fixed in the process, all worth knowing about:

  • helm_release.ingress_nginx needed wait = false (tofu/modules/core-addons/main.tf). Helm’s default wait behavior blocks until this LoadBalancer Service gets an external IP — which on a from-scratch bootstrap it never does in time, since MetalLB’s IPAddressPool is GitOps-managed and can’t exist until ArgoCD (which itself depends on ingress-nginx) has synced. A genuine bootstrap-ordering circularity that never surfaced before, because every prior apply was incremental against an already-assigned IP.
  • mock_outputs_allowed_terraform_commands needed "destroy", not just "init", "validate", "plan" (every terragrunt.hcl with a dependency block). Without it, any command against a downstream unit hard-fails with Unknown variable: dependency the moment its upstream has no real outputs — either never applied, or already destroyed — which meant run --all destroy couldn’t clean up a stack that a failed apply had left partially applied. Safe to add: a unit with nothing real to destroy never invokes its provider regardless of whether the mocked value is real, and reverse-DAG ordering means a unit that does have something real to destroy always still has its upstream intact. "apply" is still deliberately excluded — the property that matters (keycloak-realm’s keycloak provider always uses a real, known admin password, never a mock) is unaffected.
  • oauth2-proxy’s Ingress needed nginx.ingress.kubernetes.io/proxy-buffer-size: "16k" (tofu/modules/keycloak-realm/main.tf). A real scripted login through Keycloak consistently 502’d on /oauth2/callback with upstream sent too big header while reading response header from upstream in the ingress-nginx logs — oauth2-proxy’s session cookie bundles Keycloak’s access/ID/refresh tokens, comfortably exceeding ingress-nginx’s default proxy buffer. This one predates the Terragrunt refactor (same architecture, same missing annotation, on the original flat module too) — it just hadn’t been hit before. Verified fixed with the full scripted login flow again, confirming a real 200 with X-Auth-Request-User/-Email present.

Beyond those three, repeated back-to-back destroy/recreate cycles against the same physical Proxmox hardware (done deliberately, well beyond a single verification pass, to pressure-test the one-command claim under adverse conditions) surfaced real flakiness that current evidence points at environmental strain rather than a defect in this refactor: a transient DNS failure resolving factory.talos.dev, and Talos VMs that repeatedly failed to become network-reachable for several cycles in a row, even though Proxmox reported them created and the VLAN’s own gateway stayed reachable throughout — resolved by simply trying the apply again once the physical hardware had a chance to settle. A single destroy/recreate (not four in an hour) is the realistic operating pattern.

Standing up prod for the first time (rather than just re-testing dev in isolation) surfaced a different class of bug: dev and prod had never actually coexisted against the same 3 physical Proxmox nodes before, so anything implicitly assuming there was only ever one environment went untested until then.

  • proxmox_virtual_environment_download_file.iso’s filename was derived from the download URL (tofu/modules/talos-cluster/main.tf), and dev/prod share an identical Talos version and schematic, so the URL — and therefore the default filename (nocloud-amd64.iso) — was identical too. Prod’s first-ever apply hit File already exists in the datastore, it was created outside of Terraform on every shared Proxmox node, since that file already belonged to dev’s own Tofu state. Fixed with an explicit file_name = "talos-${var.cluster.name}-nocloud-amd64.iso".
  • ceph_rbd_client_key in secrets.enc.yaml was a single flat value, silently correct only for whichever environment’s key happened to be stored there — see Ceph-Backed Storage for the fix (a per-environment map) and the ceph-csi provisioner-caching gotcha it surfaced alongside it.
  • A kubernetes provider “Unexpected Identity Change” error on keycloak_postgres’s StatefulSet, blocking every subsequent plan/apply against that unit. Root cause: the resource was created during an earlier apply that failed partway through (a StatefulSet ... is not finished rolling out timeout, itself caused by the PVC being stuck on the ceph_rbd_client_key bug above) — its provider-tracked identity metadata never got populated correctly as a result. terragrunt state rm kubernetes_stateful_set_v1.keycloak_postgres followed by terragrunt import ... keycloak/keycloak-postgres (the real resource was already correct; only Tofu’s own state needed re-syncing) resolved it. Worth knowing this class of error can recur any time an apply is interrupted partway through creating a resource under this provider/OpenTofu combo — not specific to Postgres or to Ceph.

The destroy path surfaced two more, both transient rather than code bugs, on the final verification pass:

  • keycloak-realm’s destroy issues real DELETE calls against the live Keycloak API (to remove clients/users/the realm itself) — a Delete "https://keycloak.<domain>/admin/realms/homelab/users/...": EOF hit once, apparently from something else in the same run --all destroy making that connection briefly unreachable mid-request. Resolved by simply retrying; nothing to fix in code.
  • A leftover cert-manager ACME Challenge CR can wedge a namespace in Terminating forever. core-addons destroys cert-manager itself before some namespaces that had certificates mid-renewal finish cleaning up — if a Challenge object’s finalizer.acme.cert-manager.io hasn’t cleared yet, it never will once cert-manager’s own controller is gone, and kubectl get namespace <ns> -o json’s .status.conditions shows SomeFinalizersRemain indefinitely. kubectl patch challenge <name> -n <ns> -p '{"metadata":{"finalizers":[]}}' --type=merge clears it (the Challenge is a transient ACME-flow tracking object, not real data — safe to force through). Same deadlock shape as the external-secrets CRD-finalizer issue above, different controller.
