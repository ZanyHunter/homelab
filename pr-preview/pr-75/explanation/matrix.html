ZanyHunter's Homelab

Matrix (Synapse)

Synapse, the reference Matrix homeserver implementation, plus Element Web as its web client (#57), apps/matrix/. The most architecturally involved app onboarded into this repo to date — heavier upfront user consultation than usual, since several of its decisions are genuinely one-way doors or break with how every other app here is built. This page covers the “why” behind each of those; see Deployed Apps for the hostname/storage/auth summary table.

Storage: three volumes, three different backends

  • Postgres (hand-rolled postgres:16-alpine, same uid-70 pattern as Keycloak’s/Paperless-ngx’s/Vikunja’s own Postgres), Ceph-backed, 10Gi — messages, room state, device keys, account data. Synapse’s own docs recommend Postgres over SQLite for anything beyond the smallest personal deployment.
  • media_store (uploaded images/videos/files), NFS-backed, 30Gi. Unlike Jellyfin’s media library, this is fresh/empty and genuinely per-environment — a normal dynamically-provisioned PVC on the existing nfs-dev/nfs-prod StorageClass, same shape as Paperless-ngx’s document library. No static PV, no shared export, no exception to “dev and prod share no infrastructure.”
  • Synapse’s signing key, Ceph-backed, 1Gi, mounted at /data — Synapse auto-generates the key file on first boot if it doesn’t exist yet. Gets the standing backup.velero.io/backup-volumes annotation, same as Postgres: issue #57’s own acceptance criteria only call out the Postgres PVC, but this repo’s rule is every Ceph-backed workload’s data volume gets the annotation, no exceptions — losing the signing key is real, non-reconstructable state, not a re-derivable cache.

homeserver.yaml: three files, each a whole logical unit

Synapse’s config loader accepts multiple -c/--config-path files, merging them at startup — used here to keep secrets out of the plain, reviewable config, same motivation as every other app’s ExternalSecret-templated config in this repo. What’s genuinely different for Synapse: Synapse’s own docs don’t document whether that merge deep-merges nested lists/dicts or simply lets the last file’s top-level key win. Rather than guess, every key that needs a secret value lives as one complete, self-contained block in exactly one file, never split field-by-field across two:

  • synapse-config.yaml (plain ConfigMap) — the static majority: server_name, listeners, media_store_path, federation_domain_whitelist: [], enable_registration: false, report_stats: false. No database: key at all, not even a placeholder.
  • matrix-secrets.enc.yaml (ksops, no Tofu counterpart) — the entire database: block (including the non-secret host/port/user fields, kept together with the password for the same whole-block reasoning) plus Synapse’s three internal secrets (registration_shared_secret, macaroon_secret_key, form_secret). These have no Tofu-generated counterpart, same as every hand-rolled Postgres app’s DB password here — nothing outside the cluster needs to know them.

As of #74, that’s the whole list — a third file, synapse-secrets-externalsecret.yaml, used to render the entire oidc_providers block here the same “whole block, one file” way, mirroring Immich’s own “render the whole document, not just the sensitive field” pattern (immich-config-externalsecret.yaml). It’s gone: Synapse no longer holds any Keycloak client credentials of its own at all, delegating every login to Matrix Authentication Service instead (see the MAS section below). The Jinja/Go-template escaping trick that file needed ({{ "{{" }}/{{ "}}" }}, so ESO’s own Go-template render pass didn’t try to evaluate Synapse’s {{ user.preferred_username }} as one of its own fields) moved wholesale to MAS’s own equivalent mas-secrets-externalsecret.yaml — same collision, same fix, new file.

The collation gotcha, researched before deploying

Synapse hard-requires the database to have C collation/ctype and refuses to start otherwise. Alpine’s postgres image (musl libc, no real locale data) does not reliably give you C collation just by virtue of being Alpine — real-world Synapse deployments hit this even there. Fixed explicitly via POSTGRES_INITDB_ARGS: "--locale=C --lc-collate=C --lc-ctype=C --encoding=UTF-8" on the container (postgres.yaml) rather than assumed — confirmed live afterward via SELECT datcollate, datctype FROM pg_database, both C.

Apex identity: a deliberate exception to every other app’s hostname shape

Every other app’s Matrix ID/username-equivalent lives under a subdomain. The user chose the opposite for Matrix: user IDs are @user:thepugh.family (prod) / @user:dev.thepugh.family (dev), not @user:matrix.<domain> — a real, deliberate one-way-door decision (server_name can never change later without an entirely new, unportable identity), confirmed explicitly rather than defaulted.

This requires serving /.well-known/matrix/client at the bare domain_name itself — the first thing this repo serves at an apex hostname rather than a subdomain:

  • matrix-wellknown.yaml: a small nginxinc/nginx-unprivileged static server (chosen specifically so it runs non-root on 8080 with no arbitrary-uid workaround needed) serving one static JSON file, Ingress bound to the literal domain_name value, path-scoped to /.well-known/matrix/*. Deliberately does not serve /.well-known/matrix/server (the federation discovery file) — with federation off, it has no functional purpose, and it’s one fewer templated token to get wrong.
  • Synapse’s own subdomain (matrix.<domain>) is where clients actually connect after being redirected by that discovery file — server_name (identity) and the real API hostname are deliberately different values, unrelated to each other mechanically.
  • Local DNS gap: the existing wildcard record (*.<domain_name>) never matches the bare, zero-label apex. Both environments need a new, explicit unifi_dns_record (tofu/modules/network/main.tf) — written but not applied without the user’s explicit go-ahead, per this repo’s standing Unifi guardrail (a genuinely new Unifi-managed resource, not a config change to an existing one).
  • Public reachability (prod only): Cloudflare’s CNAME flattening natively proxies the literal zone apex, so a new cloudflare_record for bare thepugh.family is mechanically identical to any subdomain record. core-addons’ Cloudflare Tunnel ingress rules gained one new case — public_matrix_wellknown (env.hcl, prod true/dev false), mirroring public_keycloak_realm’s existing path-scoped-exception shape exactly, rather than trying to force this into the generic public_apps list (which assumes a full-hostname forward). Structurally can never be meaningful for dev: dev’s domain_name is a subdomain of the real apex, not the apex itself, so it could never get valid Cloudflare Universal SSL coverage there regardless. Also flagged for the user’s confirmation before applying, per the standing Cloudflare guardrail.

A real gotcha found live: pathType: Prefix rejecting a literal . in the path

The first kubectl apply of matrix-wellknown’s Ingress produced a real admission warning: path /.well-known/matrix cannot be used with pathType Prefix. ingress-nginx ≥4.12 validates Prefix-typed paths more strictly and flags a literal . (from .well-known) as needing regex-metacharacter treatment it won’t apply under Prefix semantics. Fixed by switching that one path to pathType: ImplementationSpecific — ingress-nginx’s own ImplementationSpecific behavior for a plain path with no actual regex is a normal prefix match, so this changes no real routing behavior, just satisfies the stricter validator.

A real gotcha found live: Kustomize’s delimiter/index replacement swallowing a string’s tail

The same delimiter/index technique Immich’s/Vikunja’s overlays already use to reach a token nested inside a larger text value (splitting the whole field on a character, replacing one indexed segment) has a sharp edge: the replacement swaps the entire segment, not just the token within it. matrix-wellknown’s own {"m.homeserver": {"base_url": "https://__APP_HOSTNAME__"}} had no third / after the token, so the whole trailing "}} got swallowed along with it in a real test build — caught before it reached a live cluster. Fixed by adding a trailing / after the token purely to terminate the segment (.../__APP_HOSTNAME__/"}}), harmless for a URL either way. Every other token in this app’s manifests was checked against the same requirement (immediately followed by another delimiter character) before being trusted.

Authentication: OIDC, with two real differences from every other app here

Matrix has genuine, mature OIDC support, unlike Jellyfin’s community-plugin workaround — native, well-documented delegated authentication, not forward-auth. Originally (#57) this meant Synapse’s own oidc_providers talking to Keycloak directly; as of #74 (see below) Synapse delegates that entirely to Matrix Authentication Service, which is now the thing that actually talks to Keycloak — but the two differences from every other app here predate that change and still apply, just one level removed:

  • No group-claim-to-admin mapping. Neither Synapse nor MAS has a built-in way to map a groups claim onto Matrix server-admin the way Jellyfin’s plugin or Mealie’s OIDC_ADMIN_GROUP do. Granting Matrix server-admin, if ever needed, is a manual one-time step via Synapse’s own Admin API — the same “managed by hand, not by Tofu” category as Keycloak group membership itself.
  • enable_registration: false does not block OIDC auto-provisioning — confirmed via research before deploying, not assumed, and still true post-#74 (MAS provisions new Matrix accounts on first successful Keycloak login regardless of this Synapse-side setting, which now only gates Synapse’s own native password/email signup flow). Any Keycloak-authorized identity still gets in on first use, exactly matching this repo’s “any Keycloak-authorized identity gets in” model everywhere else (Homepage, Mealie’s deliberately-unset OIDC_USER_GROUP, etc.) with zero extra config.

Public exposure: three separate decisions, not one toggle

Issue #57 itself split this into three genuinely different questions, and this repo’s answer differs per question:

  • Client-server API (matrix.<domain>) and Element Web (element.<domain>): public in prod, added to public_apps like any other app — plain HTTPS, same shape as Immich’s tunnel route, so a phone on cellular can actually reach Matrix.
  • Federation: off. federation_domain_whitelist: [] in synapse-config.yaml is the actual, authoritative control — not just omitting the /.well-known/matrix/server file, which this deployment doesn’t serve at all right now anyway.
  • Voice/video calls (TURN): out of scope for this issue, same as #57 itself flagged — see below.

Retention: deliberately indefinite

The user’s explicit choice: no retention: block in homeserver.yaml at all, meaning Synapse never purges messages or media. Mechanically this is the absence of configuration, not extra work — matches how this repo already treats Immich’s photos and Paperless-ngx’s documents as real, non-disposable personal data rather than a cache.

Deferred: real-time calling (Element Call / MatrixRTC)

The user separately asked for real-time calling with anonymous-joinable meeting links — a materially bigger, genuinely different piece of infrastructure than anything else on this page, phased out into its own follow-up issue rather than folded into #57. Research done before making that call, so it doesn’t need re-deriving:

  • That feature is Element Call, not classic Matrix 1:1 voice calls — it needs a self-hosted LiveKit SFU, a small MatrixRTC Authorization Service (lk-jwt-service, issues LiveKit JWTs — needs its own public HTTPS endpoint), and new Synapse experimental flags (MSC3266/MSC4143/MSC4222).
  • Media relay (TURN) is the same fundamental problem #57 itself already flagged for voice calls: this repo’s Cloudflare Tunnel is outbound-only with no port-forward, and TURN traditionally needs a real UDP-reachable listener. Cloudflare Realtime TURN (a managed, edge-hosted TURN service, usable independently of Cloudflare’s own SFU offering) looks like it could plug into a self-hosted LiveKit without a port-forward or a new component to operate — but this is unverified in depth and would be a new Cloudflare product/cost surface, needing the same ask-first treatment as any other new Cloudflare config.
  • Anonymous guest joining specifically requires enabling Matrix’s guest-registration flow for the calling path — the first deliberately-open-to-unauthenticated-internet surface this repo would have (everything else gates through Keycloak). A real, distinct security-posture decision, not a technical footnote.

Real-time calling (Element Call / MatrixRTC)

Split out from #57 into its own follow-up (#72) once it became clear “real-time calling with anonymous-joinable meeting links” was roughly as much new infrastructure as the base homeserver — a self-hosted LiveKit SFU, a small MatrixRTC Authorization Service (lk-jwt-service), and new Synapse experimental flags, added under apps/matrix-livekit/ as a sibling app rather than folded into apps/matrix/ itself.

This first rollout ships authenticated group calling only — no anonymous/guest joining. Research found a real, previously-unknown tradeoff: Synapse’s allow_guest_access: true opens the entire homeserver to unauthenticated account creation, not just “can join the one call a link points at” — a materially different posture than every other app in this repo, where everything gates through Keycloak with no exceptions so far. Element’s own recommended containment pattern (a second, disposable, closed-federated “guest” homeserver) properly isolates that exposure but is genuinely a second full Matrix homeserver deployment. Rather than build either speculatively, this phase targets any Keycloak-authorized identity only; anonymous joining is a distinctly-scoped later phase once authenticated calling is proven live.

No coturn, no privileged namespace — a real correction mid-design

The initial design followed LiveKit’s own “typical” self-hosting guidance: a wide ephemeral UDP port range (rtc.port_range_start/port_range_end) needing hostNetwork: true, which would have made LiveKit’s namespace a fourth privileged-PSA namespace in a repo that otherwise holds that to exactly 3 (metallb-system, csi-driver-nfs, monitoring). The user rejected that shape outright — not comfortable exposing a privileged namespace to the internet — and pointed out LiveKit supports a single-port UDP mux (rtc.udp_port, all media multiplexed over one port via SSRC identifiers) as an alternative. A single port behaves like any other Service port, so:

  • LiveKit runs as an ordinary restricted-PSA pod, no different in kind from every other app here.
  • Its media port (livekit-media, livekit.yaml) is a normal type: LoadBalancer Service, announced by the same MetalLB instance already fronting ingress-nginx (protocol-agnostic, no special UDP handling needed), pinned to a static IP the same way core-addons pins ingress-nginx’s own.
  • tofu/modules/network’s new unifi_port_forward resource forwards exactly one WAN UDP port to that IP, not a wide range.

This also closed out a real gap in #72’s own draft scope: a separate self-hosted coturn isn’t actually needed at all — LiveKit ships its own built-in TURN server, and the thing that needs a UDP-reachable path is LiveKit itself. LiveKit’s built-in TURN listener is deliberately left off for this rollout, though — it needs its own additional listener/port, and this deployment is LAN/VPN-only for now, where same-network peers connect directly and never exercise TURN at all; worth revisiting once real off-LAN usage surfaces actual restrictive-NAT connection failures, not before.

Two genuinely new NetworkPolicy shapes follow directly from this design (apps/matrix-livekit/base/network-policies.yaml): an ingress rule allowing 0.0.0.0/0 on LiveKit’s single UDP port (every other app’s ingress here only ever allows from the ingress-nginx namespace, since this port is reached directly rather than proxied), and an egress rule allowing LiveKit’s own external-IP/STUN detection (443/TCP, 3478/UDP to 0.0.0.0/0) — the first genuine internet-egress rule in this repo, everything else only ever reaching this cluster’s own ingress-nginx namespace.

Config shape

  • apps/matrix-livekit/base/livekit-secrets.enc.yaml (ksops) — LiveKit’s full config (port, rtc.udp_port, rtc.use_external_ip, its own keys block) as one file, since livekit-server takes a single --config path with no Synapse-style multi-file merge.
  • apps/matrix-livekit/base/lk-jwt-secrets.enc.yaml (ksops) — the same API key/secret pair, mirrored into lk-jwt-service’s own env vars (LIVEKIT_KEY/LIVEKIT_SECRET) — a small, deliberate duplication kept in sync by hand, same category as Synapse’s own Postgres-password duplication.
  • One shared public hostname (matrix-calls.<domain>), path-split by ingress-nginx: /livekit/jwt to lk-jwt-service, everything else to LiveKit’s own WebSocket signaling endpoint — avoids sprawling into two new hostnames for one feature.
  • apps/matrix/base/synapse-config.yaml gained experimental_features (msc3266_enabled/msc4143_enabled/msc4222_enabled) and a matrix_rtc.transports block pointing at lk-jwt-service — still fully static/non-secret, no change to the file-splitting rationale from #57.

A real gotcha found in a test build: comments count toward token-replacement math too

The Kustomize delimiter/index trick this repo uses to reach a token nested inside a larger text value (splitting the whole field on a character, replacing one indexed segment — see #57’s own gotcha with the same mechanism) treats the entire field value as one opaque string, YAML comments included. Adding the matrix_rtc block’s own explanatory comment — which happened to describe file paths using literal / characters — silently shifted the delimiter count and made the replacement land inside that comment instead of the intended livekit_service_url token, caught in a repo-server test build before it reached a live cluster. Fixed by rewriting the comment to use zero / characters at all, and confirmed this is now a standing rule for any comment placed before a delimiter/index-targeted token in this file.

A real gotcha found live: Element Web defaults to legacy calls, Element X doesn’t understand them

A real call from Element Web to a mobile Element X client failed with Element X showing “Unsupported call. Ask if the caller can use the new Element X app” — even though calls between two Element Web browser instances, on the same network, over the same LiveKit backend, worked fine. Root cause: Element Web still has two calling stacks — the plain call/video button in a room defaults to legacy 1:1 call signaling (the old m.call.* events) unless told otherwise, while only an explicitly-started “Element Call” session used the MatrixRTC/LiveKit path this repo actually built. Element X has no legacy call support at all — it only understands MatrixRTC — so it can’t do anything with a legacy call invite except reject it with that exact message. Fixed with one new key in element-web-config.yaml: element_call.use_exclusively: true, which removes Element Web’s legacy-call fallback entirely, forcing every call onto the MatrixRTC/Element Call path (the only one this deployment’s backend actually supports). No element_call.url needed — that field is for linking to a separate, externally-hosted Element Call web app, not relevant to this repo’s embedded/native MatrixRTC calling.

Deferred / not built

  • Anonymous/guest-link joining (see above).
  • LiveKit’s built-in TURN listener (see above).
  • Public exposure: matrix-calls is not in public_apps for either environment yet, and matrix_calls_public_udp_forward stays false everywhere — this phase is LAN/VPN-only, verified internally before any public exposure is considered.

Matrix Authentication Service (MAS)

Closed issue #74: Element’s “sign in with QR code” flow failed live with “Your account provider doesn’t support signing into a new device with a QR code,” traced to a real, authoritative Synapse error after deploying experimental_features.msc4108_enabled: true on its own — MSC4108 requires matrix_authentication_service to be enabled — contradicting earlier research that suggested plain Synapse could support it standalone. QR login (MSC4108) genuinely requires Matrix Authentication Service (MAS), Element’s OAuth 2.0/OIDC authorization-server architecture (MSC3861 “delegated auth”) — a real architecture change to how every Matrix login works, not an additive feature the way real-time calling (#72) was. The broken config was reverted immediately (no commits pushed for it) before #74 was researched and built properly.

A new sibling app, not folded into apps/matrix/

apps/matrix-mas/, own matrix-mas namespace — same reasoning as splitting out apps/matrix-livekit/ for #72: MAS is roughly as much new infrastructure (its own Postgres, its own public hostname, its own upstream OIDC relationship with Keycloak) as a small app in its own right, not a config tweak to Synapse.

  • MAS’s own Postgres (postgres:16-alpine, hand-rolled, same pattern as Synapse’s own) — Postgres-only, no SQLite option at all (confirmed against MAS’s docs), and unlike Synapse’s Postgres, no documented C-collation requirement, so no POSTGRES_INITDB_ARGS workaround needed.
  • MAS’s own hostname, matrix-auth.<domain> — its login UI, .well-known/openid-configuration, and OAuth2/OIDC endpoints. A normal Ingress, no different in kind from any other app’s.
  • Synapse’s side: synapse-config.yaml gained a matrix_authentication_service block (enabled: true, endpoint pointing at MAS’s internal ClusterIP address, secret_path for the shared secret) — fully static and non-secret itself (the internal endpoint is identical in both environments), placed at the very end of homeserver.yaml specifically so it introduces no characters that could shift any earlier delimiter/index-targeted token’s position (see the #72 gotcha above — still the standing rule for adding anything to this file).

The shared secret: additive, not a re-encrypt of existing state

MAS’s docs are explicit that one shared secret authenticates both directions of the relationship — MAS calling Synapse’s admin API to provision users, and Synapse calling MAS’s token-introspection endpoint to validate sessions — the same value on both sides, no separate secrets needed. Rather than add a key to the existing matrix-secrets.enc.yaml (which would mean decrypting and re-encrypting a file that already holds other live values — the DB password, registration_shared_secret, etc.), this lives in its own standalone apps/matrix/base/mas-shared-secret.enc.yaml, mirrored by an identical value in apps/matrix-mas/base/mas-secrets.enc.yaml. Deliberately additive-only, same “small duplication kept in sync by hand” category as LiveKit’s key/secret pair between two ksops files in #72.

MAS’s own config: file-indirection instead of Synapse’s whole-block convention

Unlike Synapse, MAS’s config format natively supports pointing individual scalar secret fields at a mounted file (secret_file, encryption_file, keys[].key_file) rather than needing a whole document merged in just to inject one value — cleaner than Synapse’s “whole block, one file” convention, and used here instead of it: mas-config.yaml (plain ConfigMap) holds http/matrix/secrets with every secret value pointed at /secrets/mas/*, and mas-secrets.enc.yaml (ksops) holds those files as plain Secret keys (shared-secret, encryption-key, rsa_key.pem, ec_key.pem) plus one database.yaml key holding the one block with no _file option (database.password has none) — five --config flags total on the mas-cli server invocation, MAS’s own documented multi-file merge (the same capability Synapse’s own config loader has).

One thing this split was specifically designed to avoid: mas-config.yaml’s bulk (listener definitions, trusted_proxies CIDR list, explanatory comments) is comment-and-slash-heavy, exactly the shape that already caused two real delimiter-index bugs elsewhere in this repo (the matrix-wellknown.yaml truncation and the matrix_rtc comment-slash gotcha, both above). Rather than risk a third, the two fields that actually need a per-environment token (http.public_base, matrix.homeserver) live in their own tiny, comment-free ConfigMap keys with nothing else in them at all — verified live, both substituted correctly on the first attempt.

http.trusted_proxies needed an explicit override: MAS’s own defaults (10.0.0.0/10 among others) don’t cover this cluster’s real pod CIDR (10.244.0.0/16) or service CIDR (10.96.0.0/12), confirmed live via kubectl cluster-info dump rather than assumed — without the override, MAS would attribute every request to ingress-nginx’s own pod IP for rate-limiting purposes instead of the real client.

upstream_oauth2: MAS is now the OIDC Relying Party, not Synapse

A new Keycloak client (tofu/modules/keycloak-realm/main.tf, keycloak_openid_client.mas) — MAS becomes the actual thing that talks to Keycloak, following MAS’s own documented Keycloak recipe closely: token_endpoint_auth_method: client_secret_basic (not client_secret_post, which the old Synapse client used), redirect URI shaped https://matrix-auth.<domain>/upstream/callback/<provider-id> (MAS’s own documented callback path, a fixed ULID chosen once and mirrored exactly between the Keycloak client and mas-secrets-externalsecret.yaml’s upstream_oauth2.providers[].id), and claims_imports.localpart set to action: require/template: "{{ user.preferred_username }}" — the same claim Synapse’s old user_mapping_provider used, deliberately, so a freshly MAS-provisioned account keys off the identical localpart. The old matrix Keycloak client is left in place, unused, rather than deleted in this same change — a cheap rollback path while MAS is being proven out.

A real gotcha found live: on_conflict and the account-linking step

A real login through MAS’s Keycloak upstream link failed at MAS’s own /upstream/link/ step with “Localpart not available” — not a config error, a real login that got all the way through Keycloak’s actual authentication and then hit MAS’s account-linking logic. Root cause: Synapse already had a user under that exact localpart from before this migration (the old Synapse-native OIDC auto-provisioning, keyed off the identical preferred_username claim this new config deliberately reuses — see above), and claims_imports.localpart.action: require’s default on_conflict behavior (fail) refuses to automatically link a required claim to an already-existing local user. Fixed by adding on_conflict: set to mas-secrets-externalsecret.yaml’s claims_imports.localpart — links the upstream Keycloak identity to the existing local account instead of failing, safe here since Keycloak is this deployment’s only identity source (MAS’s own docs flag on_conflict broadly as an account-takeover risk if the claim doesn’t reliably identify a unique intended user, which doesn’t apply here). Confirmed live: MAS logs show Updating provider (config re-synced cleanly) after a manual pod restart — mas-cli server only syncs upstream_oauth2/clients config into its database on startup, not on a live file-watch, so a Secret content change alone (unlike some other apps here) needs an explicit restart to take effect, the same class of gotcha as Synapse’s own ConfigMap-changes-don’t-restart-pods behavior.

Compat routing: MAS needs two paths reachable, but Ingress backends can’t cross namespaces

MAS’s docs are explicit about two routing requirements: its own hostname is the primary interface, and three legacy Matrix Client-Server API paths (/_matrix/client/*/login, /logout, /refresh) must additionally be reachable on Synapse’s own hostname (matrix.<domain>), for clients that haven’t switched to querying MAS’s issuer directly. A Kubernetes Ingress backend must live in the same namespace as the Ingress object itself, and MAS’s real Service lives in matrix-mas, not matrix — rather than a second Ingress object (and a second, redundant cert-manager Certificate for the identical hostname), apps/matrix/base/mas-compat-service.yaml is a same-namespace ExternalName Service resolving to mas.matrix-mas.svc.cluster.local, letting synapse.yaml’s existing Ingress route those three paths (matched via a regex path, nginx.ingress.kubernetes.io/use-regex: "true") to it directly. Verified live: hitting the compat login path through the Ingress and hitting MAS’s own Service directly produce byte-identical responses, including MAS’s own org.matrix.msc3824.delegated_oidc_compatibility: true marker — confirming the routing actually reaches MAS, not just that it doesn’t error.

A new NetworkPolicy shape: direct cross-namespace pod traffic, in both directions

Every NetworkPolicy in this repo before #74 only ever named kube-system/ingress-nginx/(within #72) one internet-facing ipBlock — every cross-app dependency went through ingress-nginx. The matrix_authentication_service relationship is genuinely different: MAS calling Synapse’s admin API and Synapse calling MAS’s token-introspection endpoint are both direct, in-cluster, pod-to-pod calls via ClusterIP DNS names, bypassing ingress-nginx entirely. This needed four new rules, not the usual one or two — an ingress and an egress rule in each namespace (apps/matrix/base/network-policies.yaml and apps/matrix-mas/base/network-policies.yaml), each naming the other app’s namespace by its own kubernetes.io/metadata.name label. Verified live in both directions, not just checked for syntactic presence: a debug pod inside matrix-mas reached Synapse’s admin API path (a real HTTP response, not a connection timeout), and Synapse’s own pod reached MAS’s introspection endpoint (a real 405 Method Not Allowed, not a timeout) — proving the rules are actually load-bearing.

The syn2mas migration tool: documented, deliberately not run

MAS ships a real migration tool (mas-cli syn2mas) specifically for moving an existing Synapse-native-auth homeserver’s accounts/sessions/devices onto MAS without users needing to re-authenticate — a dry-run-first, then-stop-Synapse-and-cut-over procedure. This rollout deliberately skips it: dev’s existing test account isn’t specially preserved (the user’s own call, weighed against exercising the real tool), and — more importantly — Matrix has never been deployed to prod at all, so there is no real, populated homeserver anywhere yet that this tool would ever need to run against. Running syn2mas for real, following its documented dry-run-then-cutover procedure, becomes a prod-launch-day runbook item instead of something exercised speculatively now. In practice, a fresh MAS-provisioned login reattaches to the same existing Matrix account rather than creating a divergent one whenever claims_imports.localpart’s template produces the same value the old oidc_providers.user_mapping_provider did (deliberately arranged to be true here, see above) — the session itself doesn’t survive the cutover (a new login is required), but room membership/message history tied to the existing account does, since MAS never touches that data at all.

Real-time calling (#72): confirmed unaffected, not just assumed

lk-jwt-service validates callers via Matrix’s own native OpenID token endpoint (/_matrix/client/v3/user/{userId}/openid/request_token) — a homeserver-internal mechanism MSC3861 delegation doesn’t touch (it changes how a client logs in, not how Synapse issues these federation-style tokens). A newer lk-jwt-service capability consuming a MAS-issued token directly exists for standalone Element Call deployments with no full Matrix client involved, which isn’t this repo’s setup. Verified live after MAS went in, not just assumed safe from research: the MatrixRTC transports endpoint still returns the same real auth error it did before (not a 404), and both LiveKit pods remained untouched and healthy throughout.
